Deployment

Host in the Azure WebApp

Serve /mcp from the WebApp site that deploy/bicep/templates/webApp.bicep already provisions. Reuse identity integration, stores, redaction, audit and application configuration. Disable MCP unless explicitly configured through app settings that the Bicep deployment preserves. Give it a separate ingress policy and rate limits where needed.

Transport

Remote Streamable HTTP

Use HTTPS and the SDK’s supported protocol versions. Prefer stateless request handling and explicit polling for operation results. Clients connect by URL; no local process, stdio proxy or persistent agent session is required. Do not inherit the ModelContextProtocol 2.2.0 pin from NimBus.Mcp; pin and test the ModelContextProtocol.AspNetCore version that supports the target protocol revisions.

Network reach

Reachable where the agents run

A public deployment exposes /mcp like the rest of the site, behind Entra authentication. In Spec 034 private mode, only in-network clients can reach it, so cloud-hosted agents need a path through the Application Gateway or must run inside the network. A separate Azure host remains an option if independent scaling or isolation becomes necessary; keep the transport adapter thin so that move stays possible.

Use the existing NimBus message identity. Operator queries use {endpointId, eventId} to locate the tracked message; messageId identifies a specific processing attempt and sessionId identifies ordered processing. Keep these existing identifiers explicit in tool contracts.
01b /

Replacing NimBus.Mcp.

The Spec 022 server, src/NimBus.Mcp, is a local stdio process. It lets an agent act as a bus participant through /api/agent/* and identifies itself only with an X-Agent-Id header. It sends no bearer token, so an authenticated Azure deployment rejects its calls; in practice it works only against local-development authentication. The hosted operator server replaces it. Bus participation is not carried over to MCP.

Client migration

From a command to a URL

Replace the mcpServers entry that launches dotnet run --project src/NimBus.Mcp with the deployment’s https://<webapp>/mcp URL. Remove NIMBUS_API_BASEURL and NIMBUS_AGENT_ID. In Azure, the client signs in with Entra instead of sending a header, and audit records the real user or workload. Under Aspire, point the client at the local WebApp’s /mcp; no sign-in is needed, as it is for NimBus.Mcp today.

Removal

Retire after Phase 1 is live

NimBus.Mcp is not packable (IsPackable=false), so it ships no NuGet package or public API, and removing it is not a versioning break. It still needs a release-notes entry. Keep it until the Phase 1 read tools run in Azure, then remove src/NimBus.Mcp, tests/NimBus.Mcp.Tests and their solution entries. Rewrite docs/mcp-server.md for the hosted server, and update site/features.html and the NimBus.Mcp references in Specs 032 and 034.

The REST agent API outlives this server and needs its own authorization. Retiring NimBus.Mcp does not secure /api/agent/*. Its actions check no NimBus role, and the settlement audit actor comes from the caller-supplied X-Agent-Id header. That is tracked separately from this proposal.

Contracts designed for agents

Use strict input/output JSON schemas and structured results, with concise text summaries. Typed filters only: no arbitrary SQL, KQL, URLs, filesystem paths or generic API invocation. Every response identifies its environment and asOfUtc. Lists default to 50 items, cap at 200, have opaque cursors bound to query and authorization context, and expose truncation/partial errors. Cap response bytes and time ranges; an unavailable source is never reported as zero failures.

messageVersion is an opaque server-generated state fingerprint, including latest attempt and resolution state, rather than a client timestamp. Detail responses expose eligible actions as hints; execution always revalidates them. One server URL identifies one NimBus deployment; environment switching is not a tool argument. Common errors: PermissionDenied, MessageNotFound, StaleMessage, ActionNotAllowed, FeatureUnavailable, RateLimited, OutcomeUnknown.

Keep optional MCP features optional

Use tools as the interoperable baseline. Resources can later expose endpoint catalogs and message links; prompts can offer a “triage failed messages” workflow. Neither supplies additional authority. No dependency on sampling, elicitation, client-specific approval APIs, or protocol Tasks is required for v1. Mark read tools accurately; classify is a write because it can persist results and incur provider cost. Mark skip and payload editing destructive. Annotations help clients explain actions; they do not enforce policy.

Parity gaps and deliberate exclusions

Monitor acknowledgements are currently local browser storage. Do not pretend the durable reported marker is the same thing. Shared acknowledgement requires a separate server-side model (actor, reason, expiry, endpoint), and is deferred. AI classification remains advisory; manual category overrides would also be a separate feature. Compose-new-event, invalid-message deletion, raw audit insertion, and admin bulk recovery are excluded even if reachable from a UI screen. Existing audit search can be covered by per-message history; global audit browsing can be added later under the same site-Reader restriction.

Safe retry

One durable intent per action

Bind the idempotency key to actor, client, environment, action, message, attempt and canonical arguments. Same key and same request returns the original operation; changed arguments conflict. A second key for the same attempt is also blocked by a message-action guard.

Honest outcomes

Accepted does not mean recovered

Report Accepted → Dispatched → Succeeded / Failed, with OutcomeUnknown when correlation cannot prove a result. A resubmitted message can fail again. A lost HTTP response must not cause a new business action.

Mutation contract and consistency boundary

Phase 2a: guard on current state, add no new store. Today the REST resubmit and skip paths check endpoint Contributor, publish, archive the failed row, then write the audit record. They do not check that the message is still failed or that the supplied messageId is the latest attempt. The first agent write surface adds that check in the shared coordinator. Execute only while the tracked message is still failed and its latest attempt and state fingerprint match the prepared action. Write the acceptance audit before the side effect. A retry after the message moved on then fails safely with StaleMessage, and so does a Web UI action racing the agent. One gap remains: a crash between the publish and the archive leaves the row failed, so a retry can publish again. The Web UI has the same exposure today. Phase 2a is limited to interactive (delegated) callers, and the journal below closes the gap before unattended workloads can mutate.

Phase 2b: operation journal. prepare_action validates the actual stored endpoint, attempt, state, caller permissions, and action eligibility, then returns the exact impact and a short-lived action token. Proposed expiry: two minutes. Bind it to actor/client/environment, message version, action and payload hash. Executing tools accept the token, a required reason (1–1000 characters) and an idempotency key. Recheck fresh authorization and current state at submission and before delayed dispatch. Existing message eligibility rules remain authoritative. After authentication and authorization, recognize an exact journaled retry before rejecting an expired preview or changed message state: return its existing operation without executing again.

Persist the intent and pending command atomically in an operator-operation store before acknowledging acceptance. A worker dispatches the existing NimBus command with a stable operation/command ID. Claim/lease entries atomically across replicas. Persist dispatch evidence and archive failed rows only after a confirmed publish; preserve existing session ordering. Use a shared application coordinator for REST and MCP so a UI action cannot bypass the same-message guard.

A database write and a Service Bus send are not one transaction. The journal alone cannot guarantee exactly-once delivery. Neither the Resolver nor the Manager has command-level deduplication keyed to an operator operation today, so a durable command receipt keyed by operation ID must be built on the receiving side before any automatic replay after an uncertain publish. Do not rely on Service Bus duplicate detection. The provisioner deliberately never enables it on topics, because the throttle and defer path re-sends messages with their original MessageId and the broker would silently drop those copies (MessageContext.cs). Until receiver-side deduplication exists, retain OutcomeUnknown and reconcile evidence without blind re-publication.

Proposed retention: operation records for 30 days, nonreusable action receipts for the lifetime of the source attempt, and audit according to platform policy. Never silently re-execute an expired key; require a new inspected attempt. New operation storage needs Cosmos, SQL and in-memory implementations with conformance tests. If existing storage interfaces change, update their OpenTelemetry decorator too.

04 /

Authority stays with the platform.

A tool is permitted only when all four checks pass. Client prompts, tool annotations and model confidence cannot substitute for server-side authorization.

1 · Valid identityTrusted tenant, issuer, signature, audience and lifetime
2 · MCP scopeExplicit action grant for this client or workload
3 · Endpoint roleExisting Reader / Contributor ACL
4 · Current stateEligible message, allowed environment and action policy
Interactive agents

Act as the operator

Use OAuth authorization code + PKCE with Entra. Start with nimbus.observe; grant nimbus.classify, nimbus.resubmit, nimbus.skip, and nimbus.annotate separately. Intersect delegated scope with the user’s NimBus ACL.

Publish protected-resource metadata and a proper HTTP 401 challenge. Pre-register approved clients and redirect URIs initially. Verify discovery, resource/audience mapping, and refresh behavior with each intended MCP client before committing to interoperability.

Unattended agents

Act as a named workload

Use an explicitly approved service principal with application permissions; prefer managed identity or federated credentials where supported, otherwise a certificate. Bind both tenant and service-principal object ID to endpoint grants.

Default workloads to observe/classify. Resubmit requires an explicit endpoint policy and bounded rate. Skip, payload edits and handoff settlement remain disabled for unattended identities unless deliberately enabled outside MCP. Never impersonate a human operator.

Separate MCP authentication from Web UI convenience

In Entra mode the WebApp already accepts bearer tokens: the "Az" policy scheme forwards Authorization: Bearer to the JWT scheme from AddMicrosoftIdentityWebApi, and otherwise falls back to an OpenID Connect redirect (Startup.Security.cs). That scheme serves the SPA’s API audience. Register a separately named JWT bearer scheme for the MCP resource, with its own App ID URI and nimbus.* scopes, and bind /mcp to that scheme only. Do not route MCP through the "Az" selector. Never inherit cookie login redirects or Identity cookies. The one exception is local Aspire development: when the existing local-dev bypass is active, /mcp uses it too (see “Local Aspire runs need no sign-in” below). In any other mode, fail startup of the MCP feature when issuer/audience configuration is absent. Validate a trusted tenant, signature, issuer, audience, expiry and authorized client. Reject Graph tokens or tokens for unrelated APIs. Protected-resource metadata is public; operational data is not.

Support Entra-secured deployments first. An Identity-only WebApp deployment needs a separate OAuth authorization server or later federation support; a WebApp login cookie is not an MCP credential. The client-credentials path requires a client capable of obtaining app-only tokens; it is not guaranteed for every interactive MCP client. Keep issuer/token mapping behind an adapter to support another compliant issuer later.

Enforce endpoint scope before returning data

Resolve the real endpoint from stored records rather than trusting supplied IDs. Normalize endpoint identity consistently and check every target. Filter endpoint catalogs, counts, histories, logs, classifications and links before serialization. Return non-enumerating errors for inaccessible message IDs. Do not leak another endpoint through an event’s shared history or classification revision.

Preserve the existing site-Reader requirement for cross-endpoint message search and metrics until safe scoped queries exist. Endpoint-only overviews aggregate only permitted endpoint data; label them scope: authorizedEndpoints. Cache keys include effective authorization context, endpoint set, PII capability and filters. MCP Owner access still exposes only operator tools.

The current ACL snapshot can be stale for 45 seconds and can retain a last-known-good snapshot after some failures. For mutations, add a fresh, fail-closed permission check; do not assume a per-request service alone guarantees revocation. Key grants by trusted tenant and object ID, and require workload-specific grants rather than blindly inheriting human compatibility claims.

Protect payloads, logs and classification results

Default to metadata and sanitized errors. Reuse PayloadRedaction and retain PiiReader as a separately granted capability; require an additional nimbus.payload.read scope and an explicit reveal request. Apply redaction to logs, exception text, audit notes and intelligence output, not just event JSON. Unchanged resubmit uses the original server-side payload, never a masked copy returned by a tool.

Treat message bodies, errors and classification text as untrusted data. Return them in data fields; never interpolate them into tool descriptions or agent instructions. Bound length and omit secrets. Classification uses the existing provider/data policy and returns advisory provenance. It cannot directly execute an action or authorize disclosure. Raw payload access is audited and is off by default for workloads.

Prevent amplification and keep an attributable audit trail

Rate-limit per tenant/client/actor and more tightly for mutation and classification tools. Proposed initial limits: 60 reads/minute, 5 mutations/minute and one recovery operation per message at a time; tune with measured load. Add MCP policies to the WebApp’s existing RateLimiting/ setup. It already partitions admin, search and intelligence limits per user and falls back to client IP. The MCP partition key should also include tenant and client application, so one agent client cannot exhaust a human operator’s budget. The 2026-07-28 transport copies the tool name into an Mcp-Name header, so an Azure gateway can apply tighter limits to mutating tools. The server still enforces its own limits. Bound retries per attempt, query spans, payload sizes and classification concurrency. No wildcard “resubmit all” tool. A future batch tool must use an exact previewed ID set, maximum count and per-item results.

Record actor tenant/object ID, client/application ID, workload/delegated identity, endpoint/message/attempt, tool and schema version, reason, prior state, operation ID, decision and observed outcome. Write a durable acceptance/audit record before a side effect; fail closed if that record cannot be persisted. Redact tokens and payloads from logs. Extend existing audit contracts as needed while retaining the Web UI audit trail. Add OpenTelemetry spans and metrics for latency, denial, throttling, duplicate calls and unknown outcomes.

Require HTTPS, validate Origin when supplied, restrict CORS and trusted forwarded headers, and apply ingress/private-network restrictions as deployment policy. Identity remains mandatory on private networks. SDK protocol handling must not treat a connection or session identifier as authentication.

Local Aspire runs need no sign-in. The Aspire WebApp runs in Development with EnableLocalDevAuthentication=true, which activates the existing LocalDev scheme. When that bypass is active, /mcp accepts calls without a token, as the same “Local Developer” principal the Web UI uses (site Owner through the EIP_Management compatibility claim). An MCP client connects to the WebApp’s local URL, for example https://localhost:18443/mcp, with no Entra registration or OAuth metadata. Reuse the existing double gate and add nothing new: the handler refuses requests outside Development, and startup already throws if the flag is set anywhere else. Scope checks do not apply in this mode, but endpoint-role, PII and message-state checks still run, so local behavior matches production. Because nothing authenticates the caller, keep /mcp on loopback and enforce the transport’s required Origin validation. Without it, any web page open in the developer’s browser could call the local server (DNS rebinding). Audit records the local-dev user plus the MCP client name. The bypass takes precedence over Identity and Entra whenever it is enabled. With the bypass off, for example to test Identity sign-in, MCP requires Entra like any other deployment.
Human confirmation is a client experience, not a bearer-token property. Recommend displaying the prepared action and obtaining operator confirmation for skip and payload edits. A confirmed: true argument cannot prove human approval. If independently enforceable approval is required, add an authenticated approval record outside the agent’s execution channel; this is not part of the initial proposal.

Release capability in three steps.

This page proposes architecture; it does not implement the server. Delivery order puts identity and visibility first, then validates recovery guarantees before enabling agent mutations.

PHASE 1 / OBSERVE

Secure visibility

Add the opt-in adapter and bearer policy. Share read projections, endpoint authorization and redaction. Expose the read tools and existing classification reads. Deploy to the Azure WebApp, then retire NimBus.Mcp.

  • Entra discovery + client compatibility spike
  • Local Aspire mode on the existing local-dev bypass
  • Endpoint and PII isolation tests
  • Explicit registry proves admin tools absent
  • Read-only pilot in a nonproduction Azure environment
  • Remove NimBus.Mcp; rewrite docs/mcp-server.md
PHASE 2 / OPERATE

Reliable common actions

2a: extract a shared command coordinator with preview, fresh ACL checks, a current-state guard and audit before the side effect. Enable classify, report, resubmit and skip under separate scopes for interactive callers. No new store. 2b: add the operation journal, nimbus_get_operation and receiver-side command receipts before unattended workloads may mutate.

  • Stale-state and UI-vs-agent race tests (2a)
  • Crash-between-publish-and-archive tests (2b)
  • Receiver-side command receipts (2b)
  • Both storage providers verified
  • Delegated pilot, then bounded workloads
PHASE 3 / COMPLETE

Extended operator parity

Add handoff settlement, deferred recovery and carefully constrained payload editing. Validate each against existing UI semantics. Keep administrative capabilities excluded.

  • Broker-inspection and row-version checks
  • Payload validation + PII regression tests
  • Operational runbooks and client examples
  • Shared acknowledgement remains a separate decision
Implementation shape

Small adapters, shared services

Start with NimBus.WebApp/Mcp/ for registration, schemas and tools, and Services/Operations/ for reusable read/command logic. Proposed service boundaries: IOperatorQueries, IOperatorCommands and IOperatorOperationStore. Reuse FailureClassificationService and handoff services.

Use explicit AddNimBusOperatorMcp() registration, no assembly-wide discovery. Keep generated REST clients/controllers untouched; edit api-spec.yaml if REST contracts need changes. A new shared library is justified only when another host needs it.

Acceptance bar

Prove the boundaries

Test wrong tenant/audience, expired tokens, missing scopes, Reader mutation denial, revoked grants, endpoint-ID tampering, cross-endpoint history and cached PII leaks. Test prompt-injection strings as data and feature-disabled responses. Prove that tokenless calls are rejected whenever the local-dev bypass is inactive, and that local mode rejects a foreign Origin.

Inject crashes before/after publish, lost replies, duplicate keys, competing UI actions, stale previews and failed audit persistence. Verify that blocked messages preserve session order and that a new failure is never called “recovered.” Run Release tests plus live SQL/Cosmos conformance and Service Bus/Resolver integration before rollout.

Recommended decisions to carry into implementation

01

Host in the Azure-deployed WebApp. This server replaces NimBus.Mcp, which is removed once Phase 1 runs in Azure. Bus participation moves to NimBus.Agents, not MCP. A separate Azure host remains an option, not a prerequisite.

02

Use Entra and approved clients for v1 in Azure. Local Aspire runs reuse the local-dev bypass and need no sign-in. Validate the actual agent clients’ delegated and workload token flows during the first phase.

03

Make common single-message recovery the first write surface. Default unattended skip and payload editing to disabled.

04

Ship interactive mutations on a current-state guard first. Add the operation journal, polling and receiver-side receipts before unattended mutations. Never enable topic duplicate detection, and do not promise exactly-once processing until the command path proves it.

05

Preserve daily operator semantics, with the parity exceptions listed above. Do not expose a generic bridge to all existing WebApp endpoints.
