Ny integrationsplatform som erstatning for BizTalk

Adaptere, porte, filudveksling og XML-transformation som kode med tests, i stedet for konfiguration i et designværktøj. Vi har allerede mønstret i drift: WF Proxyen holder de gamle SOAP-kontrakter i luften med SoapCore og sender hver operation til det rigtige system bag facaden. Forslaget er at gøre det samme med BizTalk, én port ad gangen.

Udgåendeorkestreringer på bts-01, som WF2 kalder synkront: Medlem, Virksomhed, Navnebase, SendOutput, UM, IIS m.fl.
Indgåendeforbrugere, der kalder WF via BizTalk: LivNet, IIS, Ekstern Portal, dele af HIP, GDPR-slettemotor
C#forretningslogik ligger i dag inde i BizTalk som kode. Den skal ud og leve som egne services.
Uændretfor forbrugerne: SOAP-facaderne beholder WSDL, URL og header-konvention
API-gateway

Én indgang for synkrone kald

YARP i en ASP.NET Core-host på IIS eller som Windows Service, som WF2 kører i dag. TLS, adgangspolitik og rate limits pr. rute, korrelations-id hele vejen igennem. Ingen containere, ingen cloud-kontrolplan.

SOAP-facader

Strangler med SoapCore

Samme bibliotek og samme SOAP-plumbing som WF Proxyen. Indgående kontrakter serveres fra de eksporterede WSDL'er og oversættes til REST. Udgående får hver Ser*Url peget på en adapter, når den er klar. Rollback er en URL.

Adaptere, filer & XML

Porte og transformation som C#

Ét adapter-projekt pr. bagvedliggende system: REST, SOAP og filudveksling over FTP/SFTP med kvittering og dubletkontrol. XML-transformationer skrives som kode med fixture-tests i stedet for maps. Kontrakt-tests seedes fra optaget BizTalk-trafik.

Egne services & messaging

Logikken ud af BizTalk

Det, der i dag er C#-kode inde i orkestreringerne, flyttes ud som selvstændige (mikro)services, der taler med platformen via API og en messaging service. Messaging bærer de asynkrone flows (DHS-notifikationer, breve, medlemshændelser) med rækkefølge pr. sag og genkørsel fra en konsol.

En fælles forundersøgelse først. Ingen forpligtelse til mere, før vi har set tallene.

Det eneste, ingen af os ved i dag, er hvad orkestreringerne faktisk gør, hvor meget C#-logik der ligger i dem, og hvilke filflows der går gennem BizTalk. Det kan kun afdækkes med integrationsteamets BizTalk-viden og WF-teamets kendskab til kaldene. Derfor beder vi om én bølge sammen, ikke et projekt.

Bølge 0 · hvad vi gør

Opdagelse og kontraktopsamling

  1. Eksport af BizTalk-applikationerne: bindings, orkestreringer, maps, pipelines, porte og den C#-kode, der ligger i dem.
  2. Inventar over WSDL'er på bts-01, FTP-lokationer og hvem der kalder eller leverer hvad.
  3. Trafikopsamling pr. port og pr. filflow, med CPR/CVR maskeret fra dag ét.
  4. Én tabel: hver port og hvert filflow, dens forbruger eller fagsystem, volumen, sideeffekter og foreslået skæbne: facade, adapter, egen service eller messaging.
  5. Pilot bagefter, hvis tabellen holder: SerNavnebase, kun læsning, høj volumen, rollback ved URL-skift.
Hvem bidrager med hvad

Tre roller, ét bord

  • Integrationsteamet: BizTalk-eksport, kontrakternes og filflowenes historik, den C#-logik der ligger i orkestreringerne, driftskrav, kontakt til systemejerne bag IISYS, UM, Navision og Output Manager.
  • WF-teamet: SoapCore-proxyens mønster, adapter-skabelon, kontrakt-tests seedet fra emulatorerne, WF2's kaldeflader.
  • Udviklingschefen: mandat til bølge 0, tid i begge teams, og åbning for servicekonti hos systemejerne, som i dag stoler på BizTalk's Windows-identitet.
Hvorfor sådan

Læring pr. port og lav risiko

  • Vi lærer pr. port i stedet for at satse alt på ét skift. Læsning først, skrivning når idempotens er bevist, forbrugerne til sidst.
  • Logik og transformationer bliver kode med tests, som både udviklere og kodende agenter kan bygge videre på og verificere.
  • Microsofts egen anbefaling er iterativ migrering. Vi følger den, men med C# og tests som mål i stedet for et designværktøj.
  • Kontaktpunkterne findes allerede: URL-nøgle pr. service, UseSer*Emulator-toggles, ProxyRouting.
Beslutning vi beder om: ja til bølge 0 og en workshop med begge teams. Resultatet er en port- og filflowtabel og et go/no-go på piloten. Det fulde forslag med arkitektur, bølgeplan og risici: IP After BizTalk.
