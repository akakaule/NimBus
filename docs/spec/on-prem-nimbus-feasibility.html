01 / FEASIBILITY

Preserve the product behavior; change who provides it.

Recommended investigation path: RabbitMQ quorum queues + a SQL Server session runtime + .NET worker hosts. Keep NimBus’s handler contracts, Resolver, tracking model, and management experience where practical.

Feasible on premises

The repository already contains SQL Server tracking and outbox providers, worker hosting, and local Identity support. Azure storage and Entra ID need not be mandatory for the proposed profile.

FIFO requires more

A session key in a RabbitMQ header is just metadata. Queue-level single active consumption does not supply Azure’s per-session state and failure isolation. RabbitMQ SAC

Go to a proof of concept

Validate ordered recovery and stale-worker handling before broad transport abstraction. Feasibility is supported by code analysis; correctness, capacity, and operational cost remain unproven.

Confirmed requirements: SQL Server is the on-prem storage baseline. A failed message must block only its own session/entity; unrelated sessions must continue, including those sharing the same broker partition. “On premises” means the core runtime can operate without Azure connectivity. No target message rate, session count, latency, retention, or recovery time was supplied.

ADR-001 intentionally makes Azure Service Bus a core capability. This concrete on-prem requirement justifies reconsidering that decision. A new ADR should authorize a second provider while retaining the Azure default; the existing ADR has not been changed. Current ADR-001

04 / PROPOSED ARCHITECTURE

Separate ordered intake from business execution.

Persist each delivery before acknowledging it to RabbitMQ. Then process durable session heads independently, so a slow or failed handler cannot hold up the broker intake partition.

Ordering contract

Key = (tenant if used, endpoint, SessionId). New business messages retain broker acceptance order per key through serial intake. Only the lowest nonterminal sequence is eligible; later messages wait until it succeeds or is explicitly skipped. Different endpoints have independent order.

Concurrent publishers do not have a meaningful global “send time” order. If domain order must survive independent publishers, send retries, or outbox dispatch races, introduce an authoritative producer sequence/admission service, with gap detection and durable buffering. Arrival order cannot reconstruct missing causal order.

Intake contract

Start with one active intake consumer per fixed partition, prefetch 1, serial SQL commits, uniform message priority, and a fenced partition lease. Admission deduplicates before allocating a new per-session ordinal. ACK only after commit. Handler work runs separately.

Pin queue settings that preserve requeue order and validate failover. Partitioning must use a stable, versioned hash of the full session key; route all event types for that key together. Do not increase partition count without draining or a migration barrier. RabbitMQ ordering constraints

Critical distinction: ACK now means “NimBus has durably accepted responsibility,” not “the business handler finished.” Queue depth alone no longer represents pending work. The WebApp must show broker intake backlog, SQL pending/blocked work, and tracking projection lag separately.

Use event-type exchange bindings for fan-out into endpoint intake queues; use explicit NimBus routing metadata for targeted controls. RabbitMQ’s direct/topic/header routing is not a replacement for Service Bus SQL filter expressions or rule actions that rewrite To/From. Compile the supported catalog into bindings and provider-side routing, and reject unsupported filters explicitly. Exchange semantics

06 / SESSION STATE REPLACEMENT

A small state blob is no longer enough.

Create a transactional execution store, distinct from Resolver’s historical tracking. The following schema and interfaces are proposed, not present in NimBus today.

RecordMinimum dataInvariant
SessionFull key; next admission ordinal; head sequence; status; blocked event; lease owner/expiry; monotonic fencing token; row versionAt most one valid owner may claim or advance the head. Use database time and compare-and-swap transitions.
Pending messageEndpoint + stable delivery identity; original event/message IDs; session ordinal; payload; attempt; due time; stateUnique delivery identity and unique key/ordinal. Payload commit and sequence allocation are one transaction. A redelivery reuses the existing row.
Outcome + outboxResolution/failure/handoff; outgoing responses/events; deduplication identity; dispatch statusHead advancement, terminal state, and response outbox commit together. Broker publication retries retain stable IDs.
Recovery commandCommand ID; endpoint/session; original blocked message; expected version; retry/skip decision; operator auditCommands are idempotent and compare against current state. A stale command cannot unblock a newer failure.
Intake partitionTopology/hash version; owner lease; fencing tokenOld intake owners cannot commit after failover. A duplicate delivery never receives a later ordinal.
Ready→Running head→Blocked / retry due / handoff→Retry same head or skip→Advance cursor

After a normal success the next head can run immediately. Retry due-times delay the head itself, so later messages never overtake it. A future new scheduled event receives its ordering position when admitted at its due time, unless the product explicitly chooses reserved sequence slots. Cancellation and dispatch must race through an atomic state transition.

Contract direction: introduce focused capabilities such as ISessionCoordinator, IOrderedMessageStore, and ITransportManagement; make park/complete/unblock transactional operations rather than public read-modify-write counters. Retain existing Azure APIs through compatible adapters. SQL can expose deferred counts as derived/cached values instead of treating independent increments as the source of truth.

Control path: retry, skip, and handoff completion target the blocked head and use the same session concurrency boundary. They must be admitted even while business execution is blocked. Treating them as ordinary work queued behind the failed head would deadlock recovery.

07 / WHERE CORRECTNESS IS WON

Design the crash boundaries before the happy path.

Failure windowRequired response
SQL unavailable before intake commitDo not ACK. Pause intake and let the broker retain responsibility. Resume through bounded backoff; never continue business work using cached session state.
SQL committed; broker ACK lostRedelivery resolves the same admission identity and ordinal; no second pending item. Then ACK safely.
Worker crashes while handlingRetain the same head. A replacement acquires a new fence; commits from the old fence are rejected. All claim, renewal, outcome, and advancement operations enforce the fence.
External side effect succeeded; completion lostBroker/SQL cannot roll back a remote CRM/ERP call. Require destination idempotency plus ordering/version checks, or a shared business transaction where possible. Existing inbox record-on-success alone leaves this crash window.
Old worker resumes after lease expirySQL fencing protects SQL, not a remote HTTP service. Propagate a validated fence/version to the destination or keep the session blocked for reconciliation until the old outcome is known. Cancellation alone cannot guarantee no late side effects.
Outcome committed; response not publishedDurable outbox resumes publication. Resolver deduplicates. A publish confirm does not certify handler completion; unroutable mandatory returns must also be handled. Acknowledgement semantics
New arrivals during replayAppend after the durable existing backlog and process through the same head cursor. Do not create a second replay consumer that bypasses ownership.
Poison message / expired messagePersist a failure and ordering tombstone; keep later work blocked until policy or an audited decision releases it. Do not silently drop the head. For broker DLX, configure and test quorum at-least-once dead-lettering; defaults are not sufficient. DLX safety
Guarantee boundary: propose at-least-once transport, one valid session owner, and ordered head advancement. Exactly-once arbitrary business effects are not promised. Strict observable FIFO during worker failover requires a compatible destination contract; where that cannot be provided, fail closed and reconcile before advancing.

Durability consequence: once broker messages are acknowledged, SQL owns the only pending payload copy in this design. A production profile therefore needs a defined SQL durability/HA and backup policy, deduplication retention covering the replay horizon, and a tested cross-system restore procedure. Broker replication cannot recover SQL rows lost after acknowledgement. Restoring an older SQL backup without a retained replay source can lose accepted work.

08 / MIGRATION SCOPE

Reuse the platform; replace the provider boundaries deliberately.

Preserve and adapt

  • Business events, session keys, handler interfaces and pipeline behaviors.
  • Resolver state transitions and SQL tracking, with transport-neutral composition and retry plumbing.
  • Inbox/outbox concepts, extended with explicit transactional completion semantics.
  • WebApp workflows and authorization, using provider capabilities and SQL pending-work visibility.

Build or extract

  • RabbitMQ sender, envelope mapping, confirms, returned-message handling and intake pump.
  • SQL session runtime, fenced claims, ordered admission, retries, scheduling and control commands.
  • Provider-neutral SDK composition: the current SDK directly references NimBus.ServiceBus.
  • RabbitMQ topology/management, worker hosts for Resolver and Function-based adapters, packaging and conformance tests.

On-prem deployment profile

Use .NET workers/services or containers for endpoints and Resolver, ASP.NET Core for Operations, SQL Server for tracking/session storage, and RabbitMQ. Aspire can compose local development; production installation and upgrades need their own deployment/runbook profile.

For an HA candidate, evaluate three RabbitMQ nodes with quorum queues replicated across them, redundant workers/WebApp, and a suitably durable SQL topology. A three-member quorum tolerates one unavailable member while retaining a majority; loss of majority pauses work. This is a starting topology, not a measured SLA. Quorum guidance

Use existing local Identity as the baseline; enterprise SSO integration is a separate requirement. Package certificates, secrets, migrations, telemetry, backup/restore, and upgrade procedures. Disable development authentication bypass. A fully open-source stack would additionally require a new supported storage provider such as PostgreSQL; that provider was not found among the repository’s listed providers.

Cutover from an existing Azure installation

For the first release, prefer new on-prem installations or an offline cutover: stop publishers, drain active sessions, inventory blocked/deferred/scheduled work, then migrate that work with its identities and ordering metadata before switching routes. Audit retained legacy deferred sequence references. Never let Azure and RabbitMQ execute the same session concurrently. A live bridge needs its own sequence, deduplication, and ownership handover design and is outside the initial POC.

Effort assessment: high for session correctness and cross-provider recovery; medium-to-high for management, hosting, and packaging; relatively low for basic RabbitMQ send/receive. A working happy-path demo would not establish production feasibility. Estimate delivery dates only after the POC measures the session design and the required capability list is agreed.

Recommendation: proceed with a bounded RabbitMQ + SQL session-runtime POC. Keep Artemis as a comparison if reducing custom coordination is more important than standardizing on RabbitMQ. Retain the Azure provider and avoid a broad generic messaging framework.
