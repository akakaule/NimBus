IP · Integration platform investigation · continues the 14 September NimBus proposals

Replace BizTalk one port at a time.

IP already runs a strangler façade in production: the WF Proxy re-publishes twenty .asmx contracts with SoapCore and routes each operation to the old or the new engine. This proposal applies the same move to BizTalk itself. Adapters, ports and maps become C# projects with tests. A gateway carries the synchronous edge, NimBus carries the asynchronous one, and SoapCore keeps every existing SOAP consumer unchanged until it chooses to move.

The switch mechanisms exist: a per-service URL key and a DI toggle for every outbound client, a routing table per process and case type for inbound calls, and a SoapCore façade proven against dozens of consumers.

Verified from IP.WF2.0

BizTalk is a protocol bridge in both directions.

The wiki page Integrationer and the architecture page describe one host, bts-01, that most backend calls pass through, and that most consumers use to reach the workflow engine. Nothing in the repository suggests BizTalk owns business state; it owns contracts, credentials, transport and whatever the twelve orchestrations do between WF2's request and the backend.

Three details from the code sharpen the picture. Every outbound URL has the shape http://bts-01/ser<Name>BTS.Published/WcfService_ser<Name>BTS_Orchestrations.svc, so each service is a BizTalk orchestration exposed through the WCF publishing wizard, not a pass-through receive port. BizTalk also serves versioned contract metadata from a WsdlRepository path (for example version 34_0_0_0 for IIS refunds), so it is IP's de-facto schema registry. And the SOAP header every caller must send lives in the namespace http://BTS.Common.Schemas.Header: the caller-identity convention across IP is itself a BizTalk schema.

What WF2 does not have today: no message bus of any kind (no MSMQ, Service Bus, RabbitMQ or NServiceBus), no SFTP/FILE/EDI, no XSLT. The existing strangler

The WF Proxy already is the pattern. Reuse it, don't reinvent it.

ADR-002 describes a SOAP façade that keeps twenty Execute360 endpoints and roughly 79 operations byte-compatible for consumers while routing each operation to WF1 or WF2. The decision logic is small and lives in code and one routing table.

Façade

SoapCore 1.2.1.16 on net10.0 exposes twenty paths under /serWorkflow/*.asmx, case-insensitive, with XmlSerializer and BOM-less UTF-8. Consumers change nothing. A second host serves SerGDPR.svc with the DataContractSerializer.

Switch

ProxyRouting holds one flag per process and case type. IsCaseInNewWF uses the GUID shape of a case id. ConnectorOptions toggles WF, Execute360 and Execute360Noop.

Merge

Fourteen search and inbox operations call both backends with Task.WhenAll, then deduplicate, sort and paginate in domain services. This is the costly part of any strangler and is already written.

Four more IP assets carry over directly:

  • SOAP plumbing already hardened against real clients. IP.ProxyWorkflow.API.Common/SoapMessage/ holds the pieces every façade needs: a message processor that adds xsi/xsd declarations to <Body> because some HIP clients require them, a custom envelope class forcing the soap: prefix, a logging middleware with buffering limits, and a middleware that lifts SOAPAction into route values for IP's call-audit component. Package this as the platform's SOAP SDK rather than copying it.
  • Caller identity convention. The SOAP layer uses no transport authentication. The caller is identified by the standard Header element (Aktoer, InitSystem, Proces) in the body, which the proxy translates into x-api-key and ip.initsystem.* HTTP headers towards WF2. New façades inherit this contract unchanged.
  • Outbound switch per client. Every one of the 21 ISer*Client registrations has a URL key and, for eleven of them, a UseSer*Emulator flag that swaps the WCF client for a REST client in DI (ADR-005). Repointing a URL to a platform adapter needs no WF2 code change; adding a second toggle value for "platform adapter" is a one-line DI change.
  • Emulators as contract fixtures. Thirteen emulators under src/Shared/IP.Emulator.Ser* reproduce the external contracts with admin endpoints for test state. Recorded BizTalk traffic can seed the same emulators to prove a new adapter answers the way BizTalk did.

ADR-002 lists the negatives honestly: a network hop, merge complexity, throwaway code and SoapCore's partial WCF coverage. The plan below keeps the façade layer thin and time-boxed, and moves the reusable parts (adapters, mappings, contract tests) into the platform that survives BizTalk.

Target architecture

Three planes replace one MessageBox.

BizTalk conflates the synchronous edge, the asynchronous bus and protocol adaptation. Separating them lets each plane use the best .NET component and lets the SOAP façade be retired independently when the last consumer moves.

Gateway plane

  • Single hostname and TLS for all synchronous entry, SOAP and REST alike.
  • ASP.NET Core authentication per route: Negotiate/Kerberos for on-prem Windows consumers, client certificates, or JWT/OIDC for new consumers.
  • Rate limiting, request/response logging with a correlation id that the façades and adapters propagate into NimBus.
  • No mapping and no business logic. Routes are configuration reloaded at runtime.

Façade plane (temporary)

  • Inbound: SoapCore endpoints serving the WSDLs BizTalk publishes today, translating to WF2 REST calls or NimBus events.
  • Outbound: SoapCore endpoints implementing the ISer* contracts WF2 consumes, delegating to adapters. This is optional: WF2 can call adapters over REST once a client is switched.
  • Every façade has a retirement condition written down: "last consumer moved" or "client switched to REST".

Adapter and messaging plane

  • One adapter project per backend system, following docs/building-adapters.md: translation, publish, subscribe, reliability boundary.
  • NimBus topics carry document notifications, letter status and member events with session ordering per case or person.
  • Tracking, Resolver and the WebApp replace BizTalk tracking and suspended-instance handling.
Strangler seams

Three seams, each with a switch IP already owns.

A strangler only works where traffic can be redirected without touching the caller. IP has three such places. Each is listed with its mechanism, its proof and its failure mode.

Seam A · inbound

Consumers → BizTalk → WF

Mechanism. Point the consumer's DNS name or the BizTalk IIS site at the gateway. A SoapCore endpoint serves the same WSDL from file (WsdlFileOptions) and forwards to WF2 REST, exactly as the WF Proxy does for Execute360 URLs. Identity travels in the SOAP body header, so a proxy hop loses nothing.

Proof. Replay captured request envelopes against BizTalk and the façade; compare response XML canonically. Health check per façade route.

Failure mode. BizTalk-published contracts may differ from WF's own (orchestration-published schemas), and BizTalk may translate between them today. Wave 0 exports them; if a contract embeds mapping, that mapping moves into the façade as C#.

Seam B · outbound

WF2 → BizTalk → backend

Mechanism. Change Ser*Url for one service to a platform adapter that implements the same contract. Optionally extend the UseSer*Emulator toggle to a three-way mode: BizTalk, adapter, emulator.

Proof. Contract test: the adapter must satisfy the recorded request/response pairs seeded into the existing emulator. For writes, the adapter must reject duplicate Unique_id/operation keys.

Failure mode. BizTalk may enrich or split messages the backend expects (debatching, cross-reference tables), and it currently authenticates to backends with its own Windows identity over TransportCredentialOnly. Each adapter needs a service account the backend owner accepts. Read-only lookups go first because a wrong answer is visible and reversible.

Seam C · asynchronous

Notifications and letters

Mechanism. DHS document notifications, Output Manager status and member events become NimBus events. The wiki's system-landscape proposal already asks for the DHS notification to go asynchronous over a queue.

Proof. Session isolation test from the earlier proposal: a failed notification blocks only its case; other cases continue. Duplicate delivery does not create a second case action.

Failure mode. A message provider that runs on-prem is still a proposal. Start on Azure Service Bus where connectivity allows, or keep seam C last.

Why not route at the network level? ADR-002 rejected DNS/load-balancer routing because operations within one SOAP service need different targets. The same holds here: a single BizTalk-published service may front two backends. Route per operation in code, switch per service in configuration.

Façade recipe, as the WF Proxy does it

Keep the shape identical for every façade so a coding agent can produce the next one from the previous one. Implementation classes are thin: authenticate, map, call, map back, fault.

// As wired today in src/Proxy/IP.ProxyWorkflow.API/Program.cs (lines 157, 180, 430-457)
builder.Services.AddSoapCore();
builder.Services.AddSoapMessageProcessor(SoapMessageHelper.AddSchemaElementsToBody()); // xsi/xsd on <Body> for HIP clients

var encoder = new SoapEncoderOptions();
encoder.WriteEncoding = new UTF8Encoding(false);                     // UTF-8 without BOM

endpoints.UseSoapEndpoint<ISerWorkFlowController>(
    "/serWorkflow/SerWorkflow.asmx", encoder, SoapSerializer.XmlSerializer, caseInsensitivePath: true);

endpoints.UseSoapEndpoint<ISerSagstrinController, SoapEnvelopePreFixCustomMessage>(  // 16 of 20 use this
    "/serWorkflow/SerSagsTrin.asmx", encoder, SoapSerializer.XmlSerializer,
    indentXml: false, omitXmlDeclaration: false, caseInsensitivePath: true);

// Contracts: [ServiceContract(Namespace = "http://ipf.dk/webservices/")] with explicit Action URIs and
// lower-case operation names to preserve the wire contract. No [FaultContract]; errors travel as
// ReturVaerdi { ID, Beskrivelse } in the response body, ID == 0 meaning success.

Two changes for BizTalk façades. First, serve the WSDL from the exported files with WsdlFileOptions instead of letting SoapCore generate it; the WF Proxy generates today and gates metadata by AD domain, which is fine for WF's own contracts but not for byte-fidelity to BizTalk's WSDL repository. Second, check the generated Reference.cs clients for XmlInclude, SoapInclude or SoapDocumentMethod usage per contract; those are SoapCore's documented gaps and are the trigger for CoreWCF on that one façade.

Authentication runs in two different models, and only one of them is a problem. Inbound, callers are identified by the SOAP body header, so façades behind a gateway see exactly what BizTalk sees today. Outbound, WF2 authenticates to BizTalk and BizTalk to backends with Windows credentials (BasicHttpBinding, TransportCredentialOnly, app-pool identity). An adapter that calls a backend directly must run under an account that backend trusts, or use Kerberos constrained delegation. That is a conversation with each backend owner, and it starts in wave 0. The GDPR host is the exception on the inbound side: it relies on IIS Windows authentication and a hand-edited web.config allow-list, which the gateway should replace.

Clean up while moving, not after. Two copies of BaseClientConfigurator exist (shared and proxy), and the proxy's HTTPS path uses a permissive certificate validator (CertificateValidatorForTest, revocation off). The adapter SDK gets one binding factory with real certificate validation; neither of the existing copies is carried forward.

API gateway

Build the gateway on YARP; adopt a product only for the developer portal.

The earlier proposal put a full API gateway outside the initial release. For IP it belongs inside, because the strangler needs one stable edge that both SOAP and REST consumers can be pointed at. The requirement is an edge, not an API-monetisation product.

Messaging

NimBus replaces the MessageBox where IP needs order and recovery.

Most of IP's BizTalk traffic is synchronous request/reply and needs no bus. Three flows are asynchronous by nature and currently rely on BizTalk pub/sub or on REST polling. They are the messaging candidates.

DHS document notifications

Today: DHS → Proxy → POST /documents/notifyupdateddocument synchronously. Proposed in the wiki: asynchronous over a queue. As a NimBus event with session key = case or CPR/CVR, a failing notification blocks only its case and can be resubmitted from the WebApp.

Output Manager letters

Today: SendOutput2Request over WCF via BizTalk with a tracking Unique_id. As a command on a topic, the adapter owns retries and the idempotency key; WF2 steps stop waiting on OM latency.

Member and company events

Changes in Medlem/Virksomhed that today reach WF via BizTalk subscriptions become events other systems can also subscribe to, which is the one capability BizTalk had that point-to-point REST loses.

Asynchrony changes WF2's failure model. Today roughly 43 workstep services call backends synchronously inside an AutomatiskStep and rely on its three retries. Turning a call into a published command means the step completes before the backend answers, and failure surfaces later in the Resolver instead of in the case. That is a behaviour change per step, so seam C is decided flow by flow, not globally.

Transport reality. NimBus runs on Azure Service Bus. The on-prem RabbitMQ provider is a design in the feasibility page, not code. If IP's baseline is fully disconnected, seam C waits for that provider or for a decision to allow Service Bus with hybrid connectivity. Seams A and B do not depend on it.

Code-first model

One repository layout for every adapter and façade.

The layout mirrors NimBus's adapter guide and the Dataverse adapter under adapters/, so IP's integrations and NimBus's own samples look the same to a developer or a coding agent.

    IP.Integration.ContractTests/   # WSDL diff, envelope canonicaliser, emulator seeding from captures
Ports
A port is an interface plus one or more transport implementations. Configuration selects the implementation; tests run against the in-memory one. This is the UseSer*Emulator idea generalised.
Maps
A map is a pure function from source contract to target contract with a fixture folder of input/expected pairs. Mapping tests are the cheapest regression net in the whole migration and the first thing a coding agent should produce.
Bindings
Per-environment values (URLs, credential references, timeouts) live outside code and are validated against bindings.schema.json at startup, replacing BizTalk binding files.
Definitions
integration.json lists ports, maps, events and their session keys. The NimBus catalog export and the gateway catalogue read it; humans do not hand-edit it.

For coding agents, the task pack from the earlier proposal applies unchanged: source and target schemas, sample envelopes captured from BizTalk, mapping rules, identity and session keys, allowed ports, error classification and acceptance fixtures. An agent should be able to produce a new façade or map from the previous one plus its fixtures without touching the SDK.

Sequence

Waves, ordered by reversibility.

Read-only lookups move first because a wrong answer is visible and harmless. Side-effecting services move once idempotency is proven. Inbound consumers move when the gateway has carried outbound traffic for a while. The asynchronous seam is last unless a transport decision lands earlier.

  1. Discovery and contract capture

    Export every BizTalk application: bindings, orchestrations, maps, pipelines, custom components, receive/send port configuration, tracking settings. Inventory published WSDLs on bts-01 and their consumers. Capture request/response traffic per port for two weeks. Classify each interface: pass-through, mapping-only, or orchestration.

    Gate: a table with one row per BizTalk port, its consumer or backend, message volume, side effects, and a target seam. This page's tables are the draft.

  2. Foundation plus one lookup

    Gateway host, façade template, adapter SDK, contract-test harness seeded from captures, observability with correlation ids, PII redaction. Move SerNavnebase (read-only, high volume, simple) through seam B.

    Gate: recorded BizTalk responses and adapter responses match canonically for all captured operations; rollback is a URL change.

  3. Outbound lookups

    SerMedlem reads, SerVirksomhed, SerSager reads, SerFogP, SerTillidsrepNavision, SerUMKontrol. Each is a new adapter project produced from the template; maps ported from XSLT where script-free, otherwise rewritten in C#.

    Gate: each adapter passes replay tests and runs a week in production without BizTalk fallback.

  4. Outbound side effects

    SerSendOutput, SerUnderskrift, SerIISRykker, SerIISTilbagebetaling, SerUMBTS, SerMedlem writes, SerSager close. Adapters enforce operation keys; where the backend offers none, the adapter keeps a durable ledger and reconciles before retrying.

    Gate: duplicate-delivery and lost-response tests produce exactly one backend effect; the ledger is queryable from operations.

  5. Inbound consumers

    LivNet, IIS, Ekstern Portal, HIP. Gateway takes the hostname; SoapCore façades serve the exported WSDLs and call WF2 REST. Consumers that want REST get a versioned route on the same gateway and the façade for that consumer is retired.

    Gate: no consumer configuration changed except DNS or a base URL; envelope replay matches; Windows-auth consumers authenticate at the gateway.

  6. Asynchronous flows and decommission

    DHS notifications, Output Manager status and member events onto NimBus topics with session keys. Retire the last BizTalk hosts and the outbound façades that seam B no longer needs.

    Gate: session-isolation and duplicate tests pass on the chosen transport; BizTalk hosts stopped for one full month before licences lapse, ahead of April 2028.

Risks

What could make this plan wrong.

Discovery

Hidden BizTalk logic

Orchestrations with convoys, cross-reference tables, BRE policies, FILE/SFTP or SQL adapters to systems WF2 never sees. Each would add a row and possibly a new port type. Wave 0 exists to find them; budget for surprises.

Maps

Script functoids

BizTalk maps compile to XSLT 1.0 and script functoids emit msxsl:script, which .NET 10 rejects (SYSLIB0062). Those maps must be rewritten in C#. The count is unknown until export.

Identity

Windows authentication through a proxy

Negotiate/Kerberos identity is connection-bound and does not flow through YARP to a destination. The gateway must authenticate and then assert identity to façades by token or header over an internal trust boundary. Design and test this in wave 1.

Transport

On-prem messaging is unimplemented

NimBus's only provider is Azure Service Bus. Seam C either waits for the RabbitMQ provider design to become code or accepts a cloud dependency for the bus. Neither blocks seams A and B.

Latency

Two hops where there was one

Gateway plus façade plus adapter adds hops. For synchronous lookups inside WF2 steps this is measurable. Prefer switching WF2 clients straight to adapter REST endpoints once a service is migrated, and keep outbound façades only where a client cannot be rebuilt.

Ownership

Throwaway versus platform code

ADR-002 calls the proxy temporary. Façades are temporary; adapters, maps, contract tests and the gateway are not. Put them in different projects from day one so retirement deletes cleanly.

Data

PII in every envelope

CPR and CVR numbers are routine payload fields. Gateway logs, tracking stores and replay fixtures need redaction and access control before the first capture in wave 0, not after.

Contracts

Metadata is stale and lives in BizTalk

No BizTalk WSDL or XSD is checked into IP.WF2.0; ConnectedService.json files still name net6.0/net8.0 targets and hosts other than bts-01. Wave 0 pulls every contract into the repository, versioned, the way the test client tree already does for WF's own services.

Timeline

Twenty months to April 2028

Six waves with production soak time is tight. If wave 0 finds more than the twelve outbound and four inbound interfaces listed here, plan for extended support or a parallel team.

Pilot

Prove it with SerNavnebase and one inbound consumer.

The pilot is wave 1 plus the smallest inbound case. It exercises all three planes except messaging and produces the templates every later wave copies.

Pilot gateObservable pass condition
Contract fidelityFor every captured SerNavnebase operation, the adapter's response equals BizTalk's after canonicalisation. WSDL served by the façade validates the same client proxies.
Switch and rollbackChanging SerNavnebaseUrl moves traffic; changing it back restores BizTalk within one deployment, with no WF2 code change.
Gateway identityA Windows-authenticated consumer reaches an inbound façade through the gateway and is authorized by group; the façade sees a trusted identity assertion, not the Kerberos ticket.
ObservabilityOne correlation id links a gateway access-log line, a façade span, an adapter span and the backend call. No CPR/CVR in any log line.
MappingOne XSLT map runs unchanged through XslCompiledTransform; one script-functoid map is rewritten in C# with fixtures proving identical output.
Agent onboardingFrom the SerNavnebase adapter, exported WSDL and fixtures, a coding agent produces the SerVirksomhed adapter with passing replay tests and no SDK changes.
OperationsA failed adapter call is findable by case id, shows the request without PII to non-privileged operators, and can be retried by an operator with an audit entry.

Proposed decision: approve wave 0 now (export and capture, four to six weeks), and the pilot on SerNavnebase behind it. Defer the messaging transport decision until seam C is reached, and revisit the NimBus + Elsa versus WSO2 comparison from the earlier proposal only if wave 0 finds orchestrations that WF2 steps cannot absorb.
