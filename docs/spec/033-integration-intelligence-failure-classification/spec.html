Spec 033 · NimBus Integration Intelligence · first module

Failure Classification

An operator investigating a Failed or DeadLettered message presses Analyze and gets a structured assessment: what kind of failure this is, and whether retrying the unchanged message is likely to help. TypeSafe Jev produces it from evidence NimBus already stores, and it appears as an advisory card on the event-details page. Settlement, session ordering, retry policy, dead-lettering, resubmit and skip are untouched.

§2 · §5

One repository, one seam

Failure Classification ships in this repository as an optional, MIT-licensed extension project. The seam is a dependency and activation boundary, not a commercial one: only the WebApp references the extension, the way it references NimBus.Extensions.Identity, and it is off by default. While it is off, no service is registered, its controllers are removed, no schema is created and no outbound call is possible. The existing test suite, run with the feature disabled, is the regression gate.

  • WebApp ProjectReference plus AddNimBusIntegrationIntelligence, gated on Enabled

Integration Intelligence

New project in NimBus.sln · NimBus.Extensions.IntegrationIntelligence · published as Akaule.NimBus.Extensions.IntegrationIntelligence

  • Options with contained validation. No licence key, no entitlement check
  • Input builder, PII redactor and secret-key scrubber

The MVP hosts in the WebApp only. The Resolver never references the extension: there is no automatic classification, so nothing runs in the processing path and Jev availability cannot touch throughput.

One failure occurrence, not one event

A classification targets a single attempt. The same event fails differently after a resubmit, and the operator wants the assessment of this attempt. Identity is FailureMessageId, the message id of the error row being viewed. The endpoint is derived from that stored row and authorization runs against it; a caller-supplied endpoint never authorizes a row belonging to another endpoint. Coordinates may be loaded before authorization, but no evidence, cached classification or history is returned or sent to the provider before it.

Eligible only when the row is an error row and the event's current status is:

Failed DeadLettered

Rejected with 409 Conflict:

Pending Deferred TooManyRequests Unsupported Published Completed Skipped any non-error row

Retained for querying and display: EventId, EndpointId, SessionId, EventTypeId.

§4

What changes outside the extension project

The WebApp is zip-deployed from a published build (nb deploy apps); operators have no host project of their own. Because the extension now lives in this repository, the stock WebApp references it and ships it in that build, exactly as it ships the Identity extension. No dynamic assembly loading, no extension-host contract and no deploy-tool change is needed. Three further integration points live in platform projects because they are reusable regardless of this feature.

4.1 · WebApp wiring

NimBus.WebApp.csproj gains a ProjectReference to the extension. Startup.ConfigureServices calls AddNimBusIntegrationIntelligence after AddStorage. When Enabled is false the method registers only a controllers-disabled feature provider and returns, following IdentityControllersDisabledFeatureProvider.

// Startup.ConfigureServices
var storageProvider = AddStorage(services);
services.AddNimBusIntegrationIntelligence(
    Configuration, storageProvider);

// disabled (default): no services, controllers removed,
// every /api/integration-intelligence/* route answers 404

It is a plain IServiceCollection method, not an INimBusBuilder extension: the feature adds no pipeline behavior and no lifecycle observer, and the invariant forbids it from doing so.

4.2 · SPA card

The card and its small fetch client live in the WebApp SPA at components/event-details/intelligence-card.tsx. It probes GET /api/integration-intelligence/status?endpointId=… for the endpoint being viewed; a 403, 404 or non-Ready status hides the card. It re-probes on endpoint navigation and discards stale responses.

The extension's routes are not in api-spec.yaml: NSwag generates a server interface the WebApp project itself must implement, which would pull the controllers out of the extension and defeat disabled-means-absent. Identity's /account/* routes follow the same rule. The client is hand-written against the API contract, and the status response carries contractVersion so a mismatched SPA hides the card instead of rendering garbage.

4.3 · Audit type

Append FailureClassified last to MessageAuditType (Cosmos persists numeric values) and add failureClassified to all three auditType enum lists in api-spec.yaml. AuditTypeContractTests pins the round-trip. The value is generic, "an analysis ran on this event"; everything provider-specific goes in the audit Data field.

4.4 · Full payload redaction

A separate capability in NimBus.Core.Messages.PII. EventJsonMasker implements it alongside IEventJsonMasker, reusing the contract traversal, but Redact replaces every sensitive leaf with *** regardless of its Redact, PartialReveal or Hash mode. Unknown-type and invalid-JSON fail-closed markers are preserved. Existing Mask behaviour and third-party implementations stay compatible.

public interface IEventJsonRedactor
{
    string Redact(string eventTypeId, string eventJson);
}

If the capability is unavailable, the extension's input builder omits the payload. Falling back to Mask or raw JSON is forbidden.

§7 · §14

What happens when the operator presses Analyze

Classification is on demand only. ClassificationMode = OnDemand is the only value in MVP; Automatic is reserved. Zero latency in the processing path, data leaves the environment only when someone decides it should, provider cost accrues only for failures someone investigates, no durable work queue, and real-world accuracy is established before any automatic mode is considered.

The POST runs these steps in this order. Cached and rejected requests still authorize and audit.

Gate: may stop the requestWork: builds or persists something
  1. Authenticate
    Anonymous callers get 401.
  2. Load message coordinates
    GetMessage(eventId, messageId), which is why routes carry both ids. Unknown message: 404.
  3. Authorize on the stored endpoint
    Contributor on the row's own endpoint (same tier as Resubmit and Skip). Never the caller-supplied endpoint. Otherwise 403.
  4. Feature ready
    Enabled and provider configuration valid. Disabled routes never reach this point (404); ProviderNotConfigured means no provider call is possible.
  5. Load that endpoint's event status
    GetEvent(endpointId, eventId).
  6. Eligibility
    Error row and status Failed or DeadLettered, else 409.
  7. Atomic cache check and reservation
    TryBeginAsync returns Cached, Acquired, InProgress, PreviouslyFailed or OutcomeUnknown. Only Acquired continues to the provider. Store unavailable with no reservation: 503, no provider call.
  8. Build input
    Exception fields, counters, filtered recent history, optional payload.
  9. Redact
    PII layer then secret-key scrubbing, both before any truncation.
  10. Provider call
    One TypeSafe request carrying all four questions. 20-second total budget including retries.
  11. Derive guidance
    Code composes the signals into FailureGuidance. Jev is never asked what NimBus should do.
  12. Conditional completion
    CompleteAsync inserts the immutable classification if the reservation's ownership token is still current.
  13. Audit, then return
    One FailureClassified row via IAuditLogService.LogAuditAsync, best-effort, on success and access-denied branches alike.

Request ids are scoped to the failure. The client generates one UUID per deliberate Analyze or Re-analyze action and reuses it for transport retries; a reused id with different force semantics returns 409. An in-process lock may reduce contention but is never the correctness gate. The POST is registered under the WebApp's existing rate-limiting policies with a dedicated policy name, since each call costs provider tokens.

§8 · §9

What leaves the environment

The provider receives the input as a JSON object state, not a prompt. Descriptive top-level keys help the model relate parts of the state:

{
  "failure": {
    "eventType": "CustomerUpdated", "endpoint": "DynamicsToERP", "status": "Failed",
    "retryCount": 3, "retryLimit": 5,
    "exception": { "type": "CustomerNotFoundException",
                   "message": "Customer 4711 does not exist", "source": "Erp.Adapter" },
    "deadLetterReason": null
  },
  "recentHistory": [
    { "attempt": 1, "outcome": "ErrorResponse", "errorType": "CustomerNotFoundException", "errorMessage": "Customer 4711 does not exist" },
    { "attempt": 2, "outcome": "ErrorResponse", "errorType": "CustomerNotFoundException", "errorMessage": "Customer 4711 does not exist" }
  ],
  "eventPayload": null
}

Mapping

Exception.Type from ErrorContent.ErrorType; Exception.Message from ErrorContent.ErrorText, redacted before truncation to MaximumErrorTextLength; Exception.Source from ExceptionSource, assembly name only.

Jev's per-request budget is 64k tokens, 32k for state plus the longest question. The builder enforces MaximumStateCharacters after truncation, dropping history first and payload second. Input tokens only are billed, so state size is the cost lever.

Recent history rules

  1. Filter by the target row's EndpointId (ordinal, case-insensitive) and SessionId (ordinal); keep only failure rows.
  2. Exclude the target row and any row enqueued at or after the target's timestamp. Equal timestamps have no proven causal order and are omitted.
  3. Order by EnqueuedTimeUtc, then MessageId; take the last MaximumHistoryItems, applied only after filtering. Attempt is a 1-based ordinal among earlier failures, not a transport counter.
  4. Redact before truncating history error text to 500 characters.

DeadLetterErrorDescription never leaves. The existing ResponseService.FormatDeadLetterDescription uses exception.ToString(), which includes stack traces and inner exceptions. It is never parsed or used as a fallback, even when ErrorContent is absent. Only the separately stored, scrubbed DeadLetterReason and safe exception fields are sent; null exception fields are valid evidence for a dead-letter occurrence.

Two redaction layers, both before the provider call

1 · PII redaction

With IncludeEventPayload = true, the target failure's payload goes through IEventJsonRedactor.Redact. Every [Sensitive] leaf is fully redacted, including PartialReveal and Hash fields; the caller's PiiReader capability never changes this. Unknown types, invalid JSON or a missing redactor cause payload omission, never raw fallback. EventPayloadIncluded is set only when a redacted payload survives the final size limit.

Independently of export, IEventJsonMasker.TryCollectSensitiveValues runs on each source row's payload to scrub quoted sensitive values from its error text and dead-letter reason. If the payload is missing or cannot be analyzed, those free-text fields are withheld. This local inspection does not opt the payload into export.

2 · Secret-key scrubbing

IIntelligenceDataRedactor walks every string-valued field of the input and replaces the value of any object key matching, case-insensitively:

passwordsecretclientSecrettokenaccessTokenrefreshTokenauthorizationapiKeyconnectionStringcookiebearersharedAccessKey

Free text is scanned for Authorization: Bearer …, SharedAccessKey=…, Password=… and AccountKey=…; the matched value becomes [redacted]. The list is extensible via configuration.

Both layers run before length truncation so a cut cannot hide a secret pattern from the scanner. If an error-text field contains an embedded exception dump or stack frames, the whole field is omitted rather than trimmed. Host secrets, NimBus auth tokens, connection strings, Service Bus credentials, the TypeSafe API key, Entra tokens and cookies are never read from configuration into evidence. Scrubbing is defence in depth, not a guarantee that arbitrary unlabelled secrets are recognised.

§10 · §11

One request, four narrow questions

TypeSafe System One call

POST https://api.typesafe.ai/v1/systemone with Authorization: Bearer <ApiKey>. Body: { model, state, questions }. All four questions go in one request; Jev evaluates them in parallel. Response: { model, answers, usage } with input_tokens and output_tokens.

  • A choice answer carries choice, probabilities (sum 1.0) and confidence (0–1). A noul answer carries only noul, the probability of "yes".
  • Errors: 401 bad key, 422 validation, 429 rate limited, 529 overloaded. Only 429 and 529 are retried, bounded exponential backoff, at most 2 retries. 4xx never.
  • Model default jev-1.13.0, not jev-latest: aliases move on release and would silently change stored results. The response model field is what gets persisted.
  • IHttpClientFactory named client with the standard Microsoft.Extensions.Http.Resilience handler. TimeoutSeconds defaults to 20 and is the total budget including backoff, validated in 1–20 seconds, below the 60-second reservation. No Python, Node or sidecar.

§12 · §19

Code turns signals into guidance

Jev is never asked whether NimBus should retry, skip or dead-letter. Code composes the four signals into one of four values, evaluated top to bottom:

  1. categoryConfidence < MinimumCategoryConfidence (0.60)
    Uncertain
  2. category == transient_dependency
    && retryLikelihood ≥ RetryLikely (0.75)
    RetryMayHelp
  3. changeRequiredLikelihood ≥ ChangeRequired (0.75)
    ChangeLikelyRequired
  4. otherwise
    Investigate

Thresholds are configuration, because they must be tuned against real NimBus failures. categoryConfidence is the provider's confidence field for the Choice answer, not the top probability; both are stored. TypeSafe's published bands, below 0.5 "don't guess" and 0.5 to 0.9 "proceed with caution", are why the default floor is 0.60 rather than lower.

Architectural invariant, protected by tests. No code path calls Resubmit, Skip, Complete, Abandon or DeadLetter from these values. Sharing a repository puts this one ProjectReference away from breaking, so architecture tests assert that only the WebApp references the extension, and that the extension assembly does not reference NimBus.ServiceBus, NimBus.Resolver, NimBus.Manager or NimBus.SDK, the only public routes to Resubmit, Skip and handoff settlement, and that no type implements IFailureDispositionClassifier or a pipeline behavior. The guidance tests assert the output type is FailureGuidance, never a message control operation. The invariant is also stated in the XML doc of FailureGuidance.

Store contract

public interface IFailureClassificationStore
{
    Task<FailureClassification?> GetLatestAsync(string failureMessageId, CancellationToken ct);
    Task<IReadOnlyList<FailureClassification>> GetHistoryAsync(string failureMessageId, CancellationToken ct);
    Task<ClassificationOperationState> GetOperationStateAsync(string failureMessageId, CancellationToken ct);
    Task<ClassificationBeginResult> TryBeginAsync(string failureMessageId, string requestId, bool force, CancellationToken ct);
    Task CompleteAsync(ClassificationReservation reservation, FailureClassification classification, CancellationToken ct);
    Task FailAsync(ClassificationReservation reservation, bool outcomeUnknown, CancellationToken ct);
}

ClassificationBeginResult is a discriminated result: Cached, Acquired (with a reservation), InProgress, PreviouslyFailed or OutcomeUnknown. A reservation carries the failure id, request id, allocated revision, an unguessable ownership token and an expiry. No unguarded save or upsert exists. Reads return completed results only.

Operation state per failure, shared by every WebApp instance

  • TryBeginAsync atomically checks the cache and operation state and, if eligible, reserves the next revision before any provider call. Only one unexpired reservation may exist per failure. A repeated request id returns its original result or state and never creates another provider call, even with force. An active reservation returns InProgress to every other caller, force included.
  • Expiry is an ambiguity boundary, not permission to replay. A timeout, connection loss after sending, process crash or uncertain completion write produces OutcomeUnknown. A non-force request must surface that state without another provider call, even when an older classification exists.
  • Only an explicit force request with a new request id may supersede an expired or unknown operation. The UI warns that the previous request may have incurred provider cost. Reserving a new revision atomically invalidates the old ownership token, so a late completion from the old owner cannot persist a result or release the new reservation. Definitively failed calls may release their reservation.
  • CompleteAsync atomically inserts the classification and marks the operation complete, conditional on the current, unexpired token; repeating an acknowledged completion with the same reservation and result is idempotent. FailAsync is also conditional and never downgrades a completed operation. Revisions are never reused; failed or superseded operations may leave gaps.

This prevents competing instances from calling the provider for the same active operation. It does not promise exactly-once provider billing after a crash or an explicit re-analysis.

§15

Who may look, who may ask

The spec 026 ladder applies unchanged, via IEndpointAuthorizationService.HasRoleAsync:

None<Reader<Contributor<OwnerPiiReader, orthogonal capability
  • Reader on the endpoint: GET classification, history and status. Same as viewing the failure.
  • Contributor on the endpoint: POST analyze and re-analyze. Same tier as Resubmit and Skip.
  • PiiReader is not required for IncludeEventPayload = true, because the payload is fully redacted before it leaves. The response never echoes the payload back.

Activation replaces entitlement

There is no licence key, no signed token and no entitlement check. The feature is open source, and the only gate is deliberate deployment configuration. Enabled is not a WebApp setting: turning on an outbound data flow to a third party is an operator decision, so the MVP has no UI toggle or admin API for it. The operator's own TypeSafe API key is the only credential; provider cost and TypeSafe's terms are between the operator and TypeSafe.

§18

When the provider fails, nothing else happens

Provider timeout, 429 or 529 after retries, 5xx, 401 or 403, malformed response or network failure: the POST returns 503 with the card's unavailable message. No status change, no resubmit, no Resolver involvement, no session impact. The classification is not persisted; an audit row is still written with outcome = ProviderError, and the reservation is marked definitively failed or outcome unknown. A timeout or ambiguous persistence failure never silently makes the request eligible for automatic replay. On an ambiguous completion write, the operation is read back first: success if committed, otherwise unavailability with the reservation preserved.

§20 · §21

Tests and acceptance

Acceptance criteria

  1. Standard NimBus behaves exactly as before with the package absent; the public suite stays green.
  2. IntegrationIntelligence.Enabled defaults to false; disabled means no services, no controllers (404) and no calls. Invalid extension options never prevent host startup or existing management operations.
  3. The extension is an MIT project in NimBus.sln with no licence or entitlement check, referenced only by the WebApp. Non-Ready states never call the provider.
  4. A Contributor on the endpoint can open a Failed or DeadLettered message and request analysis; Readers can view an existing result. Capability and both buttons are endpoint-specific.
  5. One TypeSafe request evaluates all four questions.
  6. The stored result contains category, provider confidence, full distribution, the three likelihoods, model, question-set version and tokens.
  7. Repeated opens and non-force POSTs reuse a completed result unless a newer active or unknown operation requires its explicit state. Across instances, at most one reservation owns each analysis; repeated request ids never initiate another provider call.
  8. Payloads are absent by default; opted-in payloads fully redact every annotation mode and are secret-scrubbed. Stack traces and raw dead-letter descriptions are always omitted. History contains only authorized, strictly earlier target-endpoint and session failures.
  9. Re-analyze creates a new atomically allocated revision; history is immutable. Crashes never trigger automatic replay; explicit recovery warns about prior cost; late owners cannot persist stale results.
  10. Provider failures never touch NimBus message state.
  11. No code path from a Jev answer to Resubmit, Skip, Complete, Abandon or DeadLetter.
  12. Existing recovery controls unchanged.
  13. The card is labelled advisory.
  14. Token usage and request metrics are recorded under NimBus.Intelligence.
  15. All tests below pass.

§24

Open decisions

1 · Cosmos container creation under Entra data-plane RBAC

Creating failureclassifications is a control-plane operation. Confirm how the public store creates its containers on an RBAC-only deployment and ship a Bicep snippet if provisioning must own it.

2 · One package or storage satellites

A single extension package carries both Microsoft.Data.SqlClient and Microsoft.Azure.Cosmos.

Recommendation: single package for MVP; the WebApp already ships both SDKs, and splitting into .SqlServer and .CosmosDb satellites is mechanical later.

3 · ADR for the precedent

The pivot sets a pattern: AI-assisted features ship in-repo, off by default, bring-your-own provider key, advisory only.

Recommendation: record it as ADR-016 with the implementation PR and cross-reference ADR-015.

4 · Per-endpoint allow-list

With no licence gate, Enabled exposes Analyze on every endpoint to its Contributors. An optional AllowedEndpoints list (empty means all) keeps sensitive endpoints' evidence in-house.

Recommendation: include it; it is one filter in the status and POST path.

5 · Storage scope for MVP

Both SQL Server and Cosmos, or SQL first, since the dev environment is SQL-backed.

Recommendation: both, because the in-memory conformance suite makes the second provider cheap and the Cosmos emulator recipe exists.

6 · Retention

Purge classifications with the event, an existing admin action, or keep them for calibration.

Recommendation: purge with the event; calibration exports are a later module.
