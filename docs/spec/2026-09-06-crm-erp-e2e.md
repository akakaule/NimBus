# CRM/ERP message lifecycle end-to-end coverage

## Scope

Extend the existing Playwright suite against the actual CRM API, ERP API, worker
and Functions adapters, Service Bus transport, Resolver, and SQL databases. Cover
the 28 scenario families listed in the conversation in both directions where the
demo supports them. Preserve native CRM publishing and ERP CloudEvents/outbox.

## Design

- Reuse the real domain APIs and handlers. Add opt-in, Development-only E2E
  controls in the sample contracts assembly, enabled by an AppHost test profile.
  Controls require a shared secret header, accept only bounded scripts for GUID
  sessions, and never activate in normal demo or production runs.
- Decorate the sample's typed handlers through their existing DI registrations.
  A session script chooses the next handler outcome (ordinary failure, configured
  retry, transient, permanent, discard, pending, or success). A separate pipeline
  probe exercises middleware failures at the correct boundary. Keep NimBus core
  unchanged unless a failing regression establishes a defect.
- Record handler attempts and completion coordinates through the control API so
  assertions can prove no handler reinvocation, retry budgets, and lineage.
- Control real ERP handoff settlement by releasing a specific registered job;
  observe Pending+Handoff and Deferred before releasing it. Do not use a short
  wall-clock race as synchronization.
- Use unique test entities and session-scoped assertions. Restore failure modes
  and test scripts in finally/fixture cleanup. Do not delete unrelated data.
- Preserve existing browser tests, update the Actions menu interaction, and use
  REST for setup and exact business/audit assertions.
- Infrastructure interruption cases run serially on an explicitly selected demo
  AppHost. Discover URLs with Aspire. Never operate on another running AppHost.

## Verification

Start with regression tests for the control guards and scripted attempt behavior,
then implement controls. Typecheck and enumerate Playwright tests. Run the live
suite against the local emulator/SQL profile, inspect failed traces and logs, and
fix demonstrated defects. Record coverage and actual verification results in the
suite README. The emulator is not a durability substitute for Azure Service Bus;
do not claim broker-restart persistence. The demo handoff job registry is currently
in-memory, so API restart durability must be treated as an explicit limitation.
