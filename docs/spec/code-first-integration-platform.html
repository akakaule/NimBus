01 / RECOMMENDATION

Yes, this is feasible. Much of the category already exists.

The strongest reason to extend NimBus is a consistent C# developer experience and one operational model for integrations, messages, sessions, and failures. Protocol support alone is not a strong reason to build a platform.

Compose with NimBus

Add reusable connectors, integration packaging, a run/step model, and operations pages. Evaluate Elsa for durable workflows. Keep uncomplicated transformations as normal NimBus handlers.

Recommended if C# + NimBus matter

Adopt a suite

WSO2 Integrator is a close match to code-oriented integration plus self-hosted management. Commercial suites such as MuleSoft and IBM App Connect cover broad enterprise integration requirements.

Recommended if breadth matters

Avoid rebuilding the engine

Durable timers, crash recovery, correlation, workflow upgrades, compensation, and distributed ownership are a separate engineering product. Choose an engine after a bounded comparison.

Keep the custom surface small
Confirmed baseline: C#/.NET-first integration authoring, with the web console for monitoring and management. Use on-prem deployment with SQL Server as the storage baseline. A failed message must block only its own session/entity; other sessions continue. Working assumptions: Git as the authoring source of truth and a deployment profile that can run without a cloud control plane. Fully disconnected deployment remains to be confirmed.

WSO2’s documented platform supports code/visual authoring, on-prem deployment and an integration control plane; Ballerina is its implementation language. This makes it a real alternative to building the broader product, not merely a source of inspiration. WSO2 overview

02 / PRODUCT BOUNDARIES

Three building blocks, one operational experience.

Connector

A reusable protocol or system adapter: receive an SFTP file, call a REST API, consume a message. Owns connectivity, authentication, rate limits, checkpoints, and protocol-specific behavior.

Example: packaged Dataverse or SFTP connector reused across projects.

Integration

A versioned business capability: validate an order, map its fields, invoke ERP, publish an outcome. Owns contracts, mapping rules, ordering scope and business error classification.

Example: PartnerOrders.Import, maintained as a C# project.

Durable workflow

An optional orchestration for waits, callbacks, approvals, multiple steps, and compensation. The chosen engine persists progress and resumes it across process restarts.

Example: submit ERP job → wait for callback → export acknowledgement.

These are proposed design mappings, not a claim of BizTalk feature parity. A full API gateway, universal visual editor, broad SaaS catalog, and B2B agreement platform are outside the initial release.

04 / PROPOSED NIMBUS EXTENSION

Keep the execution plane separate from the console.

Working name: NimBus Integrations. Ship it as optional platform capabilities and reusable packages. Publish each business integration as an immutable worker/service release.

What exists in NimBus

  • Extension registration, middleware and lifecycle observers.
  • SQL tracking, inbox/outbox, sessions, retry/recovery and pending handoff for long-running external work.
  • Code-first catalog/AsyncAPI export, web monitoring, management, identity and tracing.
  • MCP tools for topology, publishing, receiving, settlement and failure search.

What would be new

  • Integration definition/release records, bindings, connector registry and durable run/step projection.
  • Reusable REST/file-transfer adapters and ingress receipts/checkpoints.
  • A workflow engine bridge, version policy, completion reconciliation and correlated operations UX.
  • Integration templates, contract fixtures, agent task packs, build validation and deployment manifest generation.

The existing NimBus.Agents package hosts runtime agents that receive and settle business messages. That is different from a coding agent writing integration source. Reuse the catalog and tooling where useful; a runtime LLM is not required to execute an integration.

Engine selection: start with an Elsa + SQL Server spike because its documented programmatic authoring and Studio align with this stack. Dapr is the competing .NET option. Avoid a universal wrapper over every engine operation; keep a narrow bridge for start, signal, status and control, with engine-specific workflow code behind a clear package boundary. Validate persistence, multi-node locks, dispatch recovery, versioning and monitoring before selecting a production engine.

06 / ORDERING & DURABILITY

Keep one owner for each kind of state.

NimBus owns session admission

Business key scope is (tenant if used, endpoint, SessionId). An integration endpoint admits one session head; later work waits until that head is completed or explicitly skipped. Other sessions remain runnable.

Do not reinterpret workflow instance IDs as global session locks. Two workflow instances for the same customer must not bypass the NimBus gate.

The engine owns step progress

The durable engine owns workflow waits, timers, step history and resumption. The integration bridge maps one admitted NimBus message to a stable workflow/run ID and reports terminal outcomes back.

Workflow retries own business-step retries after handoff. Broker retries cover delivery/start signaling; they must not repeatedly start the whole workflow.

Admit session head→Record start intent→Start workflow idempotently→Pending handoff→Durable completion command
  1. Record before crossing systems. Commit a bridge record with message coordinates, workflow identity, version and start intent. Redelivery resumes that record. A worker dispatches the intent and handles ambiguous “start succeeded” responses idempotently.
  2. Retain the logical session block. Use NimBus’s handoff protocol to settle the broker delivery while preserving the blocked session. Do not hold a broker lock for a day-long approval. Reconcile start, handoff-established, and workflow-terminal states because they are not one atomic transaction.
  3. Persist completion. On workflow success/failure, retain an outbox command addressed to the original message and session. Wait for the handoff registration to exist before delivering an early completion. Duplicate completion must not unblock a newer failure.
  4. Keep the control lane open. A callback or recovery command must reach the blocked workflow without waiting behind that same session’s business messages. Otherwise the workflow waits for an event that cannot be consumed.
  5. Recover with the original identity. Resume a failed step/run where supported; a new run is a distinct operator action with explicit idempotency implications. The NimBus resubmit action must consult the bridge rather than start a second copy blindly.
Not an exactly-once claim: database fencing cannot stop an expired worker from making a late external API call. Use destination idempotency plus sequence/version enforcement, or hold the session for reconciliation before advancing. Compensation is a business action and can itself fail; it is not a distributed rollback.

On-prem dependency: the earlier RabbitMQ + SQL session proposal is still unimplemented. A SQL-backed workflow engine does not resolve that transport work. Prove this integration layer first using the current Azure provider, then run the same session contract suite against the on-prem provider when it exists.

Versioning and projection rules

Pin each run to an immutable integration version, workflow definition, connector version and configuration version. Keep compatible old workers available while runs drain; rolling back new deployments must not silently reinterpret old state. Use engine-supported migration/versioning mechanisms and test them.

Maintain separate records for integration releases, run/step projections, ingress receipts/file ledger, bridge/outbox state, and operator commands. Engine state and NimBus tracking remain owned by their respective components. Projections are rebuildable and visibly report lag; OpenTelemetry traces may be sampled and cannot be the sole durable audit record.

    08 / DEVELOPMENT WITH CODING AGENTS

    Give agents a constrained SDK and an executable specification.

    Ordinary C# files, stable contracts, fixtures and a one-command local verification loop are the foundation. A prompt that says “build an integration” is not enough.

    Integration task pack

    • Business requirement, source/destination schemas and sample messages/files.
    • Mapping rules, identity/correlation rules and per-session ordering scope.
    • Allowed connectors, operations and credential references; expected latency and volume.
    • Error classification, retry limits, idempotency, compensation and manual recovery rules.
    • Acceptance fixtures for duplicates, malformed inputs, partial transfers, callbacks and failures.

    Generated deliverables

    • Integration project and unit/contract tests; reusable mappings separate from I/O.
    • Versioned definition with stable integration/step IDs and binding schemas.
    • OpenAPI/AsyncAPI/schema artifacts, fixture examples and an operator runbook.
    • Container/worker packaging, release manifest, permissions and health checks.
    • Build/analyzer report and compatibility checks; a reviewable change through the existing PR flow.

Persisted/replayed workflow code must obey the chosen engine’s rules. Network access, clock reads and other nondeterminism belong in the engine’s supported activities or durable APIs.

    Task + fixtures→Scaffold→Failing tests→Code + local checks→Review + release

    Proposed tooling: nb integration new, validate, test, and pack. These are new command ideas. Build on existing catalog export instead of maintaining duplicate schemas.     Agent guardrails: generated integration code is trusted application code after review, not safe merely because an agent wrote it. Use isolated build/test credentials and synthetic fixtures. Artifact promotion grants runtime permissions; arbitrary uploaded code must not execute in the web console process.

    Measure the claim: give the same small integration task to a coding agent against each shortlisted platform. Count working acceptance tests, human corrections, unsupported API guesses and reproducibility—not just lines generated or vendor “AI” features. Agents should generate source and tests; normal deterministic integrations do not require an LLM call per event.

    09 / OPERATIONS & SECURITY

    Make the service supportable before broadening the catalog.

    ConcernProposed requirement
    IsolationDefault to a worker/container per integration or explicitly trusted deployment group. One failing or leaking connector must not take down the management UI or unrelated integrations.
    Identity & secretsUse existing NimBus authorization as the base; scoped operator actions, payload access and machine identities. Connector secrets resolve from environment bindings/secret storage. Do not store credentials in definitions or workflow history.
    Network/file boundariesAllow approved internal integration destinations deliberately. Validate addresses and redirects against connector policy; scope file roots, prevent traversal, validate host keys/certificates and bound upload/archive expansion. Do not expose arbitrary URL execution through the console.
    Durability & retentionDefine retention for receipts, deduplication keys, payloads, engine state, projections and audit. Back up and restore them coherently. Do not delete replay payloads before the maximum recovery horizon.
    On-prem installationSQL Server baseline; broker and workflow runtime services as selected; optional durable payload share/object store. Package offline artifacts if required. Runtime health must not depend on a cloud control plane in the disconnected profile.
    Release managementOne immutable artifact promoted between environments. Bindings vary, source does not. Show version drift, provide drain policy, retain old workflow workers and test schema/definition upgrades.
    Capacity & supportSet connector concurrency and per-destination rate limits, payload limits, queue/storage budgets and alerts. Measure hot-session fairness and workflow-history growth. Assign ownership for adapters, platform runtime and business incidents.
    10 / BUILD, COMPOSE OR ADOPT

    Use a vertical pilot to make the decision concrete.

    Adopt WSO2 or a commercial suite

    Choose this when the primary need is a broad connector/operations product and the authoring/runtime model is acceptable. Integrate with NimBus through defined APIs/events where necessary.

    Cost to evaluate: language/tooling change, exact edition, hosting/control plane, support, migration and the session contract.

    Compose NimBus + an engine

    Choose this when C# source, NimBus ordering and one operational experience are important. Build the connector standard, run projection, bridge and developer tooling.

    Cost to evaluate: integration maintenance, engine upgrades, failure-boundary tests, console work and on-call ownership.

    Build a complete engine

    Do not choose this as the initial plan. Only reconsider if candidate engines fail a documented hard requirement and the organization can own a durable-runtime product.

    Cost to evaluate: recovery, scheduling, distributed coordination, version migration and long-term compatibility.
