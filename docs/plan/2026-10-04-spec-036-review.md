# Review: Spec 036, one Cosmos DB tracking container (2026-10-04)

Reviewed: `docs/spec/036-cosmos-single-tracking-container/spec.md` and ADR-017, checked against the code on
`master` at e9996280 and Microsoft's Cosmos DB documentation. Three reviewers covered three areas (store and
runtime code; migration, provisioning and operations; platform facts and economics). An independent
verifier then tried to refute each finding. None was refuted; several were narrowed, and the narrowed
versions are what this document records.

Verdict: **the direction is right, but the spec isn't ready for Phase 1.** The reasons for the change hold
up: no throughput is ever set on endpoint containers, the cost arithmetic is correct, and the hierarchical
key facts match Microsoft's docs. Seven findings need design changes before implementation:

- `EndpointScope` can't express the store's existing queries.
- The cutover runbook fails on the default Flex Consumption Resolver.
- Nothing stops v5 apps from starting on unmigrated data.
- Migration reruns don't converge.
- Migration silently leaves out rows in containers whose TTL is off.
- The row-by-row purge runs inside an HTTP request.
- The isolation conformance tests contradict the "SQL Server and in-memory unchanged" scope.

The last of these exposes a live endpoint-prefix leak on SQL Server that should be fixed now, independently
of this spec.

Disposition, 2026-10-05: all 24 findings are folded into the spec and ADR-017. The spec's review trail
(§16) maps each change to its section. The SQL Server leak is being fixed separately, as a prerequisite
(spec §9).

## Findings, most important first

### Major

1. **§5.3: `EndpointScope` can't run or express the store's queries.** The sketched API only *builds* a
   `QueryDefinition` and returns an `IQueryable<EventDbo>`. Nothing executes a query. Today 13
   `GetItemQueryIterator<T>` call sites on endpoint containers use non-`EventDbo` projections
   (`IdProjection`, `StatusQueryResult`, `BlockedEventProjection`, `int`, `DateTime`,
   `SessionCountQueryResult`, `BatchSessionQueryResult`) and `QueryRequestOptions`
   (`Lookups.cs:84,128`). So store bodies would still need the raw container, which contradicts goal 3 and
   §7.3.
   - The `SELECT … WHERE … [AND ({where})] [ORDER BY …]` template can't hold `GROUP BY`
     (`EndpointState.cs:16-17`). It can't hold `OFFSET/LIMIT` either (`Search.cs:423`) without
     smuggling it into `orderBy`.
   - The spec never says how the store obtains an `EndpointSetScope`.
   - `EventDbo` is a private nested class (`CosmosDbMessageTrackingStore.cs:85`).
   - §8 says LINQ queries are checked through `ToQueryDefinition()`, but the store's LINQ paths end in
     `.ToFeedIterator()`, and `RecordingCosmosAdapters.GetItemLinqQueryable` throws `NotSupportedException`.

   **Fix:**
   - Specify the full scope surface: `Iterate<T>(QueryDefinition, token, options)`, a
     `ToFeedIterator<T>(IQueryable<T>)` seam the recording adapter can intercept, and a statement template
     with a mandatory scope placeholder (or explicit `GROUP BY`/tail slots).
   - Add a factory for the set scope.
   - Make `EventDbo` internal or nest the scopes.
   - Add a test that fails when a store method reaches a container any other way.

2. **§6.2: the runbook can't run on the default Flex Consumption Resolver.** Step 3 stops the Resolver and
   step 5 runs `nb deploy apps`. On Flex, which is the default plan (`deploy.core.bicep:69`), the zip deploy
   must run against a *started* app. `AppDeploymentService.cs:201-212` says the az CLI reports failure
   otherwise, so the command throws before it deploys the WebApp. The obvious recovery is to start the app
   and redeploy, but that runs the v4 Resolver against the frozen legacy containers, after the copy. On
   Elastic Premium, the `finally` block restarts the Resolver even when the zip deploy fails
   (`AppDeploymentService.cs:215-235`).

   **Fix:**
   - Pause the Resolver with `AzureWebJobs.Resolver.Disabled=true` instead of stopping its host.
   - Deploy v5 while the trigger is disabled, migrate, then re-enable it.
   - Have migrate check that the trigger is disabled.
   - Rehearse the exact runbook on both plans (Phase 0 or §8).

3. **§5.8, §6.1 step 5: nothing enforces the layout marker.** Three routine upgrade paths deploy v5 apps
   right after infra and topology, with no migrate step: `nb setup` (`SetupCommand.cs:130-140`), the Deploy
   NimBus workflow (`.github/workflows/deploy.yml:142,160,176`) and the Azure Pipelines template. The v5
   Resolver and WebApp would then start on an empty `unresolvedevents`:
   - Failed events vanish from the UI.
   - Their sessions stay blocked in Service Bus session state (`SessionState.cs:22`), with no row to
     resubmit or skip.
   - A later migrate verifies against a polluted target.

   In the other direction, a pre-v5 `nb container resubmit` still targets the frozen legacy containers
   (`Container.cs:150-185`).

   **Fix:**
   - Add a startup guard to the Cosmos provider: when legacy `/id` containers named after catalog
     endpoints exist and the marker doesn't list them, the Resolver refuses to process, health reports
     unhealthy, and the WebApp shows a banner that links the runbook.
   - Run the same preflight in `nb setup`, `nb deploy apps` and `deploy.yml`.
   - In the runbook, require upgrading every `nb` installation.

4. **§6.1 steps 3-4: create plus 409 means reruns never converge.** The design expects reruns after a failed
   writer check, after `--force`, and after a rollback followed by another cutover. In each case the source
   changed after the first copy. The rerun gets 409, keeps the stale target row, and fails the per-status
   verify. Content-only changes are missed silently. Only deleting target rows by hand recovers. §8's
   "idempotent rerun" test doesn't cover this.

   **Fix:**
   - Stamp `migratedFromTs` on copied rows.
   - On 409, replace the target row when the source `_ts` is newer.
   - Keep target rows that have no stamp, because v5 wrote them.
   - Add an emulator test: migrate, change a source row, rerun, and assert that the new state is copied
     and verify passes.

5. **§6.1 step 3: the "elapsed TTL" skip drops rows that are live today.** On a TTL-on source, Cosmos
   already hides expired items from queries, so the skip rule changes nothing. On a TTL-off source, item
   `ttl` has no effect, so those rows are live. `docs/storage-providers.md` documents that endpoint
   containers created before TTL was turned on are TTL-off.

   On such a source the migration silently leaves out rows the WebApp shows today: Completed, Skipped and
   archived rows older than 30 days, and soft-deleted rows. Unresolved rows are dropped too when a bounded
   `UnresolvedRetentionDays` is configured. A dropped Failed row leaves its session blocked with nothing to
   resubmit. The source containers survive, so the rows can be recovered, but the docs tell operators to
   back up before turning TTL on for exactly this reason.

   The verifiers split on severity (major and minor). It's listed as major because the loss is silent.

   **Fix:**
   - Preflight reads each source's `DefaultTimeToLive` and puts it in the dry-run report, with per-status
     counts of rows that would be skipped.
   - For TTL-off sources, copy the rows by default with a reset TTL, and skip them only behind a flag
     (e.g. `--apply-elapsed-ttl`).
   - Seed a TTL-off source in the §8 migration test.

6. **§5.5: the row-by-row endpoint purge runs inside an HTTP request.** Both entry points await
   `PurgeMessages` inline (`EndpointImplementation.cs:508`, `AdminService.Purge.cs:585`). At parallelism 2,
   100k rows take minutes and 1M rows about an hour, but App Service ends requests at about 230 s
   ([request timeout](https://learn.microsoft.com/troubleshoot/azure/app-service/web-request-times-out-app-service)).
   The purge keeps running unobserved because `PurgeMessages` takes no `CancellationToken`.
   `ClearEndpoint` and the audit entry run only once the purge returns. A retry starts a second concurrent
   purge, and a 404 from a row the other purge already deleted counts as failure.

   **Fix:** run the purge as a background operation (202 plus an operation id plus progress), or cap each
   call and let the UI loop. Also define:
   - how concurrent purges of one endpoint are prevented;
   - when the audit entry and `ClearEndpoint` run;
   - a cancellation path.

7. **§8 versus "SQL Server and in-memory unchanged": `GetEventsByFilter` matches the endpoint by prefix.**
   The contract says ID-like filters, including the endpoint id, match by case-insensitive prefix
   (`IMessageTrackingStore.cs:166`). SQL Server implements this as `EndpointId LIKE @EndpointId`
   (`SqlServerMessageTrackingStore.Search.cs:157`) and in-memory as `HasPrefix`
   (`InMemoryMessageStore.cs:265`). The A/AB isolation test therefore fails on both providers. Cosmos is
   exact today only because the filter selects the container.

   This is also a **live bug on SQL Server**:
   - `EventImplementation.Search.cs:32,65` authorizes Reader on the route endpoint and then passes it as the
     prefix filter, so a Reader on `Billing` sees `BillingV2` rows.
   - `AdminService.SkipMessagesAsync` (`AdminService.Purge.cs:549-560`) re-writes sibling endpoints' events
     as Skipped rows under the purged endpoint.

   **Fix:** make the endpoint filter exact on every provider (contract doc, SQL Server, in-memory), and
   drop "unchanged" for those providers. Fix the SQL Server leak now, separately from this spec.

### Minor

8. **§2.1, §5.5, §11 item 1: the endpoint-page purge is refused in Production and Staging only for callers
   who aren't site Owners.** A site Owner can run it in every environment, so production has two RU-heavy
   purge paths, and §11 names only one. Either correct the text and give both paths the throughput
   warning, or block the endpoint-page purge in Production and Staging for everyone.
9. **§5.9, §5.10: `RequestPriority` names the wrong owner.**
   - The store never creates its client. The DI factory in `CosmosDbMessageStoreBuilderExtensions` does,
     through the static `CreateCosmosClient(IConfiguration)`.
   - The public `AddCosmosDbMessageStore(builder, CosmosClient, …)` overload takes a client the host built,
     so the option would be silently ignored there.

   Say that the factory reads `IOptions<CosmosDbMessageStoreOptions>`. Define the behaviour for a
   host-supplied client: apply `RequestOptions.PriorityLevel` per request, or warn or reject. Add a test
   for that overload.
10. **§5.4: the paging contract for the single failed-search query is unspecified.** Today's
    `FailedEventPageCursor` gives three things the bare Cosmos token doesn't:
    - an exact `hasMore`, because it reads `need + 1`. Without it, `Truncated` misreports at exactly 5,000
      rows.
    - full pages after the `WithinDateBounds` in-memory filter;
    - lenient decoding. A stale token sent to the new query raises a Cosmos 400, which
      `CosmosExceptionTranslation` doesn't map, so the UI gets a 500 rather than "reload once".

    Apply the `UpdatedAt` bounds exactly on `updatedAtTicks` on the server. State whether the store reads
    `pageSize + 1` and wraps the token. Map a bad token to a restart at page 1 or to a 400 the UI handles.
11. **§5.7, §7.3: the copy tools bypass `EndpointScope`.** `AdminService.CopyEndpointDataAsync` and
    `Container.CopyEndpointData` build hand-written SQL in assemblies that can't reach the internal scope.
    A missing predicate would copy other endpoints' rows into another account, and no test pins it. Move
    the tracking-row copy into `NimBus.MessageStore.CosmosDb` behind the scope, as the migration logic
    already is. Alternatively, add tests that pin the exact predicate in both tools and soften the "only
    path" wording.
12. **§8: the test inventory is incomplete.**
    - `CosmosDbClientPurgeTests` covers only the session purge. The container-delete and cache-eviction
      expectation lives in `CosmosDbClientUnitTests`, along with handle caching and faulted creation.
    - `CosmosDbClientRetentionTests` pins container TTL, TTL mode, reserved-id rejection and
      differently-cased ids.

    List these tests and their replacements. Keep an explicit Cosmos unit test that `billing` and
    `Billing` stay isolated: the SQL Server collation is case-insensitive, so conformance can't pin it.
13. **§6.1 step 2: the selection rule isn't catalog-aware.** Two cases go wrong:
    - A host-configured inbox container (`CosmosInboxOptions.ContainerId` other than `inbox`) matches all
      three rules. Adapters keep writing it during the outage, so the quiet check refuses the run, and
      `--force` would import its dedupe records.
    - Orphan containers of removed endpoints are imported. Their rows then have no WebApp purge path,
      because both purges return 404 for endpoints outside the catalog.

    Intersect the selection with the catalog (the CLI already loads catalogs), or sample rows for the
    `EventDbo` shape. Report the containers it skips. Document how to clean up a decommissioned endpoint's
    rows once the Storage page is gone.
14. **§6.3: rollback after step 5 has concrete consequences the spec doesn't state.**
    - Failures after cutover leave sessions blocked with no legacy row.
    - Failed rows that were resubmitted and completed under v5 still show Failed, so resubmitting them
      again duplicates processing.
    - Redeploying v4 needs the v4 `nb`.
    - v4 doesn't reserve `unresolvedevents`, so a v4 WebApp lists it as deletable, both during runbook
      steps 2-3 and after a rollback.

    Ship a 4.x patch that reserves `unresolvedevents` before v5, and write explicit rollback steps.
15. **§6.1 step 4, §6.2 step 6: the verification can't reconcile as specified.**
    - Elapsed rows are subtracted only from the total, not from the per-status counts.
    - "Elapsed" depends on `now` at the moment each row is copied.
    - A 409 counts as present even when the target row's status differs.
    - Monitor counts exclude terminal and soft-deleted rows and are read after the Resolver drains its
      backlog, while the marker stores total rows.

    Verify per (status, deleted) against one reference time, and compare content on 409. Emit counts in
    the form the Monitor page shows, and compare before the restart.
16. **§6.4: the downtime model ignores the read side.** Legacy containers have 400 RU/s manual throughput
    (az CLI default), and each is read with `SELECT *`, two `MAX(_ts)` scans and the verify scans. A large
    endpoint makes the copy read-bound, whatever the target's max. Add source read RU per row to Phase 0.
    Model downtime per endpoint as rows ÷ min(source rate, target rate). In the runbook, say to raise large
    legacy containers temporarily; up to 10,000 RU/s is instant on one partition.
17. **§6.4, §5.1: the autoscale lever and parameter are underspecified.**
    - **Ceiling.** 10,000 RU/s is the instant ceiling for a one-partition container. Going higher starts
      a 4-6 h split that permanently adds physical partitions, thins each endpoint's share after
      scale-down, and raises the minimum max to the highest max ÷ 10. State 10,000 RU/s as the ceiling for
      the run.
    - **Parameter handling.** Name the `infra apply` option. Say whether it is pinned to the deployed value
      the way plan and SKU are; otherwise every routine `nb infra apply` resets a tuned max to 4,000.
      Document the raise and revert for the migration. Add an `InfrastructureDeployer` test.
    - **Lazy creation.** Under key authentication, if v5 starts before `nb infra apply` has run, lazy
      creation makes `unresolvedevents` 400 RU/s manual, which Bicep can't convert to autoscale. Either
      create it with autoscale throughput or warn outside the emulator.
18. **§6.1 options, §5.8: the marker contract has gaps.**
    - `--force` is used in step 1 and §11 but missing from the options list.
    - No component is named to read `settings/tracking-layout`. `IsProtectedContainer` is synchronous, and
      §5.9 freezes the storage contracts.
    - The spec doesn't say whether partial `--endpoint` runs merge into the marker (with an ETag
      read-modify-write) or overwrite it.
    - The spec doesn't say whether `--dry-run` writes the marker.
19. **§14: Phase 0 tests only a single-partition container.** At ≤10,000 RU/s with little data,
    `unresolvedevents` has one physical partition, so items 4 and 5 can't show prefix routing, fan-out, or
    behaviour after a split. The .NET SDK has had defects with hierarchical keys after splits (#4326, fixed
    in 3.39.0). It isn't shown whether open issues affect NimBus's two-level key.

    Add a live check on a container split into at least 2 partitions:
    - endpoint-scoped SQL and LINQ queries (session, `GROUP BY`, `ORDER BY`) return complete results;
    - compare the routing of `ARRAY_CONTAINS(@ids, c.endpointId)` with `IN`;
    - a failed-search token issued before the split still resumes.

    Prefer WHERE-only scoping over the optional `PartitionKey` "second fence".
20. **§5.1, §7.2: the composite indexes won't serve the queries as the scope emits them.** A Cosmos
    composite index serves a filter plus `ORDER BY` only when the `ORDER BY` lists the equality-filtered
    properties first. `EndpointScope.Query` passes `ORDER BY` through unchanged, so
    `(endpointId, event.UpdatedAt DESC)` goes unused. Have the scope prepend `c.endpointId`, with the
    direction matched, and derive composites from the real query shapes, e.g.
    `(endpointId, sessionId, event.UpdatedAt DESC)` for `Search.cs:423`. §7.2 should also say that the row
    gains two properties, not one.
21. **§7.2, §7.5: the per-endpoint ceiling is overstated.** Cosmos splits RU/s evenly across physical
    partitions, and a low-cardinality first level keeps each endpoint on one partition. So the ceiling is
    min(10,000, max ÷ physical partitions): 4,000 at the default, and 2,000 after a split. Add guidance to
    watch Normalized RU Consumption by `PartitionKeyRangeId`.
22. **§8, §7.4, §14 item 2: CI's floating emulator tag.** `vnext-latest` (`dotnet.yml:40`) changed its
    hierarchical-key behaviour through 2026: #290 was fixed, then regressed as #329 (fixed in
    `vnext-EN20260810`). #346 was fixed in `vnext-EN20260907`, not in August as §7.4 says. Pin a dated tag
    (≥ EN20260907) for Phase 1 and correct the date.
23. **§9, §10: docs and process gaps.**
    - The adapter-docs skill files still describe per-endpoint containers.
    - `.github/workflows/deploy.yml` needs the migration gate or a note.
    - The upgrade flow in `docs/deployment.md` and its Storage-tab wording need updating in v5.0.0, not only
      in Phase 3.
    - The "Reserved endpoint ids" section of `docs/storage-providers.md` needs updating.
    - `docs/versioning.md` has no maintenance-branch procedure, and 4.x is shipping actively (v4.1.0 and
      v4.2.0). Add one as a Phase 1 prerequisite.

### Nit

24. **§7.3: restore wording.** `cosmosDB.bicep` sets no `backupPolicy`, so deployments use periodic backup.
    Point-in-time restore belongs to continuous backup. The conclusion still holds (restore to a new
    account and copy the endpoint's rows back), but state the real mode.

## Verified as accurate

- **§2.1 facts.**
  - 13 reserved ids, and exactly five reserved-id call sites.
  - Endpoint purge deletes the container and evicts the cache; the session purge uses parallelism 8.
  - The TTL values.
  - The failed-search fan-out runs eight at a time with a 50,000-row histogram cap.
  - The account-scope role assignment.
  - Line drift since `f16a0369` is small and not misleading.
- **§5.4 table.** It covers every store member that touches an endpoint container. The members it leaves
  out use `messages`, `audits` or `eventreports`.
- **§5.2.** `updatedAtTicks` can be kept in sync. `event` is written only through `EventDbo` construction,
  and the patches touch only `/deleted` and `/ttl`.
- **Store wiring.** No code outside the store reaches endpoint containers except the paths the spec names.
  At runtime only the Resolver and the WebApp use `IMessageTrackingStore`, so stopping them stops every
  runtime writer.
- **Public API and versioning.** `CosmosDbMessageTrackingStore`, `FailedEventPageCursor` and
  `EndpointContainerProvisioner` are internal, so changing or deleting them breaks no public API. The
  obsolete-then-remove plans match `docs/versioning.md`.
- **API transport.** The failed-search and paging continuation tokens travel in POST bodies, so larger
  cross-partition tokens can't hit URL limits.
- **Account and cost baseline.**
  - The account is provisioned, not serverless, and has no database-level shared throughput.
  - No throughput is ever set on endpoint containers, so the N × 400 RU/s baseline is right.
  - Every figure in §7.1 and §6.4 recomputes correctly, as does the 485-endpoint limit.
- **Hierarchical partition keys.** Up to three levels, set at creation, prefix routing through `WHERE`, and
  the id recommended as the last level. SDK 3.62.1 meets the minimum version, and 3.61.0 explicitly
  supports `/id` as the last level. Patch and `ReadManyItemsAsync` work with full keys.
- **Priority-based execution.** `CosmosClientOptions.PriorityLevel`, `RequestOptions.PriorityLevel` and the
  enum are public in SDK 3.62.1. ARM `2025-10-15` carries both account properties, still labelled preview.
- **Bicep schema.** The container schema at `2021-06-15` lists `MultiHash`, partition key version 2 and
  `autoscaleSettings`.
- **Rejected alternatives.** Shared throughput, serverless, delete by partition key and copy jobs were each
  rejected for reasons that match the documentation.
- **Marker container.** `settings` exists with key `/id` and holds singleton documents, so
  `tracking-layout` won't collide.
- **Migration environment.**
  - TTL counts from the item's last-modified time, so `ttl - (now - _ts)` is the right arithmetic.
  - `nb infra apply` runs incremental deployments, so legacy containers and undeclared role assignments
    stay in place.
  - Private networking requires running migrate from inside the network, as §6.1 says.
